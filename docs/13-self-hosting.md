# 13 — Свой сервер

Сервер нужен **только для командной работы**. Одному человеку он не нужен вовсе:
локальный режим полон сам по себе ([01](01-architecture.md)).

Прочитайте сначала, что сервер даёт и чего не даёт — это определяет, нужен ли он
вам.

## Что даёт сервер, чего не даёт файл

Раздать проект коллеге можно двумя способами, и они не равнозначны.

| | Экспорт файла | Сервер |
|---|---|---|
| Коллега получает | копию **навсегда** | доступ, отзываемый в один клик |
| Видно, кто держит профиль сейчас | нет | да |
| Двое в одном аккаунте одновременно | легко, и это бан | лок не даст |
| Изменения возвращаются | нет | да |
| Права: «запускать, но не выгружать cookies» | нет | да |

Ключевое — **отзыв**. Отданный файл забрать нельзя. Уволенный сотрудник уносит
все профили, которые когда-либо открывал. Именно поэтому у команды есть сервер, а
не общая папка.

## Что понадобится

- Любой VPS: 1 vCPU, 1 ГБ RAM, 10 ГБ диска. Этого хватает на десятки человек —
  сервер намеренно «тупой»: не генерирует отпечатки, не расшифровывает бандлы,
  не проксирует трафик профилей.
- PostgreSQL 16 или новее.
- Доменное имя и TLS. Без него сессионные токены пойдут открытым текстом.

S3-совместимое хранилище (MinIO) понадобится позже, для синхронизации бандлов —
пока она не реализована, оно не нужно.

## Установка

```bash
git clone https://github.com/fury-browser/fury && cd fury
cargo build --release -p fury-server
```

Создайте базу:

```bash
sudo -u postgres createuser fury --pwprompt && sudo -u postgres createdb -O fury fury
```

Запустите. Миграции применяются сами при старте — отдельного шага нет:

```bash
DATABASE_URL=postgres://fury:ПАРОЛЬ@127.0.0.1:5432/fury BIND=127.0.0.1:8901 ./target/release/fury-server
```

Проверьте, что сервер отвечает так, как ожидает клиент:

```bash
curl -s http://127.0.0.1:8901/v1/me
```

Ответ должен быть ровно `{"error":"unauthenticated"}` с кодом 401. Приложение
использует это как признак «здесь Fury» — если ответ другой, оно откажется
подключаться, и это правильно: адрес с опечаткой иначе всплыл бы позже, при входе,
и выглядел бы как неверный пароль.

## Первый пользователь

Регистрации нет намеренно: открытая регистрация на сервере, который держит
рабочие аккаунты, — это дверь без замка. Владелец заводится вручную.

Сгенерируйте хеш пароля:

```bash
cargo run --release -p fury-server --example hash -- 'ваш-пароль'
```

Вставьте организацию и владельца:

```sql
INSERT INTO organizations (id, name) VALUES (gen_random_uuid(), 'Моя команда');
INSERT INTO users (id, email, password_hash)
VALUES (gen_random_uuid(), 'you@example.com', '$argon2id$...');
INSERT INTO org_members (org_id, user_id, role)
SELECT o.id, u.id, 'owner' FROM organizations o, users u WHERE u.email = 'you@example.com';
```

Дальше участники и выдача доступов — из приложения.

## TLS

Сервер слушает открытый HTTP и **не должен** смотреть в интернет напрямую.
Поставьте перед ним обратный прокси. Caddy делает сертификат сам:

```
fury.example.com {
    reverse_proxy 127.0.0.1:8901
}
```

Внутренний CA организации тоже подойдёт: клиент берёт корни из системного
хранилища, а не из вшитого списка, — то есть достаточно установить ваш
сертификат в систему на машинах команды.

## Модель доступа

Организация → проекты → профили. Доступ выдаётся **на проект**, не на профиль:
это единица, которой реально управляют.

Права — набор флагов: `view`, `launch`, `edit_profile`, `edit_fingerprint`,
`edit_proxy`, `reveal_secrets`, `export_cookies`, `create_profile`,
`delete_profile`, `manage_access`. Роль ставит потолок: менеджер не может выдать
больше, чем есть у него самого.

Практический смысл — вот эта комбинация, ради которой всё и строилось:

> оператор запускает профиль, но **не видит** пароль прокси и **не может**
> выгрузить cookies.

Технически это обеспечивается с двух сторон: сервер отдаёт хост прокси
замаскированным (`res***0236.provider.net`), а агент получает набор ограничений,
вычисленный на сервере, и запускает ядро с ними. Клиент их не выбирает.

## Резервные копии

```bash
pg_dump -Fc fury > fury-$(date +%F).dump
```

Этого достаточно: сервер хранит метаданные, права и лок. Сами профили (cookies,
история) живут на машинах пользователей, пока синхронизация бандлов не готова —
их бэкапит каждый у себя, каталог из `fury-agent status`.

## Обновление

```bash
git pull && cargo build --release -p fury-server
```

Перезапустите. Миграции применятся сами. Схема меняется только вперёд:
удаляющих миграций нет, поэтому откат бинарника на предыдущую версию безопасен.

## Чего пока нет

- **Синхронизации бандлов.** Профили не переносятся между машинами через сервер:
  эндпоинты выгрузки/загрузки не написаны. Команда сейчас разделяет *метаданные*
  профилей — какие есть, чей прокси, кто держит, — но не сами cookies.
- **Шифрования на клиенте.** Когда синхронизация появится, бандлы будут
  шифроваться до отправки. До тех пор не храните на сервере ничего, чего не
  готовы там увидеть.
- **Отзыва лока с чужой машины.** См. известную проблему в
  [06](06-profile-sync.md).
