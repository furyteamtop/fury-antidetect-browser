# 13 — Свой сервер

Сервер нужен **только для командной работы**. Одному человеку он не нужен вовсе:
локальный режим полон сам по себе ([01](01-architecture.md)).

Прочитайте сначала, что сервер даёт и чего не даёт — это определяет, нужен ли он
вам.

## Что даёт сервер, чего не даёт файл

Раздать проект коллеге можно двумя способами, и они не равнозначны.

| | Экспорт файла | Сервер |
|---|---|---|
| Коллега получает | копию **навсегда** | доступ, отзываемый в один клик |
| Видно, кто держит профиль сейчас | нет | да |
| Двое в одном аккаунте одновременно | легко, и это бан | лок не даст |
| Изменения возвращаются | нет | да |
| Права: «запускать, но не выгружать cookies» | нет | да |

Ключевое — **отзыв**. Отданный файл забрать нельзя. Уволенный сотрудник уносит
все профили, которые когда-либо открывал. Именно поэтому у команды есть сервер, а
не общая папка.

## Что понадобится

- VPS: 2 vCPU и 4 ГБ RAM, если сервер собирается на нём же.
  [`deploy/server-install.sh`](../deploy/server-install.sh) строит `fury-server`
  из исходников с thin LTO и первым делом заводит 2 ГБ свопа, потому что на
  четырёх гигабайтах линковка временами не помещается и падает OOM-киллом
  посреди сборки, что выглядит как загадочное зависание (:30-44). Готовый
  бинарь потом работает и на 1 vCPU / 1 ГБ — тяжёлая здесь только сборка.
- Диск считается по бандлам, а не по базе. Бандл — это цельный профиль
  браузера, Caddy принимает до 512 МБ на загрузку (:198-202), и всё это лежит
  на самом сервере в `/var/lib/fury/bundles` (:70, :143). 10 ГБ — это десяток
  профилей, а не команда.
- Сервер при этом остаётся намеренно «тупым»: не генерирует отпечатки, не
  расшифровывает бандлы, не проксирует трафик профилей. Этого хватает на
  десятки человек.
- PostgreSQL 16 или новее.
- Доменное имя и TLS. Без него сессионные токены пойдут открытым текстом.

S3-совместимое хранилище не нужно и не используется. Сервер кладёт бандлы прямо
в файловую систему: `FURY_BUNDLE_DIR`, по умолчанию `/var/lib/fury/bundles`, — и
проверяет каталог на запись при старте, до открытия сокета, а не при первой
загрузке ([server/src/api.rs:2640-2675](../server/src/api.rs)). Узнать, что
каталога нет, в момент, когда оператор закрывает браузер после рабочего дня, —
худшее из возможных времён.

Колонка в базе называется `s3_key`. Это имя от прежнего плана, а не признак
того, что где-то есть S3.

## Быстрый путь: docker compose

```bash
git clone https://github.com/fury-browser/fury && cd fury
cp .env.example .env          # задайте FURY_DB_PASSWORD
docker compose up -d
```

Всё. Поднимается Postgres и сервер, миграции применяются сами при старте.
Сервер слушает `127.0.0.1:8901` — наружу его выводит обратный прокси, см. TLS
ниже.

Проверьте:

```bash
curl -s http://127.0.0.1:8901/v1/me
```

Ответ должен быть ровно `{"error":"unauthenticated"}` с кодом 401 — приложение
использует это как признак «здесь Fury».

## Установка без docker

```bash
cargo build --release -p fury-server
```

Создайте базу:

```bash
sudo -u postgres createuser fury --pwprompt && sudo -u postgres createdb -O fury fury
```

Запустите. Миграции применяются сами при старте — отдельного шага нет:

```bash
DATABASE_URL=postgres://fury:ПАРОЛЬ@127.0.0.1:5432/fury BIND=127.0.0.1:8901 ./target/release/fury-server
```

Проверьте, что сервер отвечает так, как ожидает клиент:

```bash
curl -s http://127.0.0.1:8901/v1/me
```

Ответ должен быть ровно `{"error":"unauthenticated"}` с кодом 401. Приложение
использует это как признак «здесь Fury» — если ответ другой, оно откажется
подключаться, и это правильно: адрес с опечаткой иначе всплыл бы позже, при входе,
и выглядел бы как неверный пароль.

## Первый пользователь

Регистрация есть, но выключена по умолчанию. `POST /v1/auth/signup` отвечает
отказом, пока сервер не запущен с `FURY_OPEN_SIGNUP=1`
([server/src/main.rs:73-78](../server/src/main.rs),
[server/src/api.rs:237-247](../server/src/api.rs)); установщик пишет в
`/etc/fury/fury.env` явный `FURY_OPEN_SIGNUP=0`
([deploy/server-install.sh:145-154](../deploy/server-install.sh)). Выключена —
потому что self-hosted сервер это чья-то личная машина, и «пусть заходит любой,
кто нашёл адрес» не та политика, которую наследуют вместе с установкой.

Страшно это звучит сильнее, чем есть: каждая самостоятельная регистрация заводит
**свою** организацию, а организация — граница, по которой и так фильтрует каждый
запрос. Чужой на вашем сервере не достанет ни до чего вашего; он стоит вам строк
в базе. Приложение спрашивает `/v1/server` перед тем, как предложить форму:
сервер, который про эту ручку не слышал, отвечает 404, и это читается как «нет».

## Сервер, на который пускают посторонних

Это поддерживаемый режим, а не побочный эффект. Включив `FURY_OPEN_SIGNUP=1`, вы
получаете сервер, на котором каждый зарегистрировавшийся — **владелец своей
организации** и может вести её целиком: звать коллег прямо из приложения,
передавать им ключ организации, раздавать доступ по проектам. Это та же командная
работа, что у вас, просто в другой организации, и две организации нигде не
пересекаются.

Проверено на живом сервере 04.08.2026, две «студии» рядом:

| | владелец Студии Один | сотрудник Студии Один | Студия Два |
|---|---|---|---|
| профилей видно | 1 | 0, пока не выдан доступ → 1 после | 0 |
| логины профиля | читает | **403** (нет `reveal_secrets`) | **404** |
| лок на профиль | берёт | берёт | **404** |
| участники организации | только своей | только своей | только своей |

404, а не 403, для чужой организации — кто не видит проект, тому его не
существует; 403 подтвердил бы, что он есть. 403 сотруднику — честно: профиль он
видит, права на пароль у него нет.

### Пределы

Изоляция полная, **справедливость — нет**. Прочитать чужое нельзя никому, а вот
занять весь диск может один человек со скриптом, и первое, что вы об этом
узнаете, — база отказывает в записи всем. Поэтому перед тем как открывать
регистрацию, поставьте три потолка в `/etc/fury/fury.env`:

```
FURY_MAX_ORGS=50                    # организаций на сервере всего
FURY_MAX_PROFILES_PER_ORG=200       # профилей в одной организации
FURY_MAX_STORAGE_PER_ORG=5368709120 # байт бандлов на организацию (5 ГБ)
```

Пустое значение — без предела, и для сервера своей команды это правильно: квота,
в которую упираются в понедельник утром, хуже, чем её отсутствие.

Что важно знать про то, как они считаются:

- **организации** — считаются и удалённые. Организация удаляется мягко, чтобы её
  профили пережили ошибку, и цикл «удалил-создал» иначе делал бы предел
  декоративным;
- **профили** — удалённые не считаются: они в корзине, восстановимы, и брать за
  выброшенное деньгами предела нечестно. Проверяется на **каждом** пути создания,
  включая клонирование пачкой: потолок, который стережёт один маршрут, — это
  потолок с обходом, и обход всегда там, где создают двести штук за раз;
- **место** — по строкам в базе, а не по файлам на диске: удаление профиля
  освобождает квоту, а файл, оставшийся от падения, никому не записывается в счёт.
  Загрузка обрывается посередине, а не после приёма всего: отказ, пришедший
  вслед за целым гигабайтом, уже стоил того диска, который он защищал.

Сервер пишет выбранные пределы в лог при старте и отдельно предупреждает, если
регистрация открыта, а `FURY_MAX_ORGS` не задан.

### Старые версии бандлов

`FURY_KEEP_BUNDLE_VERSIONS=10` по умолчанию. Каждое закрытие профиля пишет новую
версию, и до 04.08.2026 ни одна не удалялась никогда — профиль, который открывают
десять раз в день, рос на десять бандлов в день, вечно. Это не злоупотребление,
это продукт в работе, и означало бы, что квота на место заполняется обычной
работой, а сервер выглядит сломанным.

Десять — потому что смысл хранить прошлые версии один: восстановление. Профиль
разлогинили, сайт стёр хранилище — нужна версия «до». Десять закрытий назад
достаточно, чтобы дотянуться до вчера, и достаточно мало, чтобы цена на диске
осталась ограниченной.

`0` отключает обрезку и хранит всё.

### Убрать организацию

На открытом сервере это понадобится: кто-то бросил организацию, кто-то
злоупотребил. Слот в `FURY_MAX_ORGS` считается за всеми организациями, включая
удалённые, поэтому брошенная занимает место навсегда, если её не убрать.

Ручки в API нет намеренно — удаление чужой организации не то действие, которое
делают из приложения. Делается из шелла машины, где стоит база:

```bash
sudo -u postgres psql -c "DELETE FROM organizations WHERE name = 'Кого убираем';" fury
sudo -u postgres psql -c "DELETE FROM users WHERE email = 'кого@убираем';" fury
```

Аудит при этом **остаётся**. Записи теряют ссылку на организацию (`org_id`
становится NULL) и переживают её — потому что момент, когда журнал нужен
сильнее всего, наступает как раз после того, как у кого-то отобрали доступ.
Осиротевшие записи не видны ни одному пользователю приложения: политика
опирается на `user_in_org(org_id)`, а `user_in_org(NULL)` ложно. Прочитать их
может только тот, у кого есть доступ к базе.

До миграции 0007 это не работало вовсе: 0006 сделала аудит неперезаписываемым,
отобрав UPDATE и DELETE у роли приложения, а каскад от удаляемой организации
выполняется **с правами владельца таблицы** — то есть у той же роли. Организацию
нельзя было удалить никому, включая суперпользователя. 0007 выдаёт право менять
ровно два столбца-указателя (`org_id`, `actor_user_id`) и оставляет запретным
всё, что описывает событие:

```
как роль fury:  UPDATE audit_events SET action='подделка'  →  permission denied
                DELETE FROM audit_events                    →  permission denied
```

Суперпользователь обходит любые права — это неустранимо и не является рубежом:
у кого есть shell на машине, у того есть и файлы базы.

## Первый пользователь, если регистрация закрыта

Первый владелец в любом случае приглашается из шелла той машины, где стоит база:

```bash
DATABASE_URL=postgres://fury:ПАРОЛЬ@127.0.0.1:5432/fury \
  ./target/release/fury-server invite --email you@example.com --org "Моя команда"
```

Команда напечатает код вида `5rrk-qgfr-gtyd-mw0f-sp12-axzy-0jsz-sx19`. Он живёт
48 часов, годен один раз и **не хранится** — сервер держит только его хеш, как и
для сессионных токенов. Потеряли — выпустите новый, это одна команда.

В приложении: «У меня есть приглашение» → адрес сервера → код → пароль. Дальше
всё происходит на вашей машине: генерируется пара ключей X25519, приватный ключ
заворачивается в ключ, выведенный из пароля через Argon2id, и рождается ключ
организации (ORK), запечатанный на ваш публичный ключ. На сервер уходит только
завёрнутое. Организация создаётся в момент, когда у неё появляется владелец.

> **Пароль восстановить нельзя.** Не «сложно» — нельзя: ORK развернётся только
> из него. Это цена того, что владелец сервера (в том числе мы, если вы
> пользуетесь нашим хостингом) не может прочитать ваши прокси и куки. Храните
> пароль в менеджере паролей.

Участники приглашаются той же командой с `--org-id` и ролью:

```bash
./target/release/fury-server invite --email colleague@example.com \
  --org-id <UUID организации> --role member
```

Такой участник заводит аккаунт сам, но **ключа организации у него ещё нет**: ORK
запечатывается на его публичный ключ, а тот появляется только после регистрации.
Пока владелец не выдал ключ, участник входит и видит структуру команды, но не
может расшифровать ни одного профиля. Это не баг, а тот же смысл, что у
приглашения: человек попросился в команду, и кто-то ещё должен его впустить.

Дальше выдача доступов к проектам — из приложения.

## TLS

Сервер слушает открытый HTTP и **не должен** смотреть в интернет напрямую.
Поставьте перед ним обратный прокси. Caddy делает сертификат сам:

```
fury.example.com {
    reverse_proxy 127.0.0.1:8901
}
```

Внутренний CA организации тоже подойдёт: клиент берёт корни из системного
хранилища, а не из вшитого списка, — то есть достаточно установить ваш
сертификат в систему на машинах команды.

## Модель доступа

Организация → проекты → профили. Доступ выдаётся **на проект**, не на профиль:
это единица, которой реально управляют.

Права — набор флагов: `view`, `launch`, `edit_profile`, `edit_fingerprint`,
`edit_proxy`, `reveal_secrets`, `export_cookies`, `create_profile`,
`delete_profile`, `manage_access`. Роль ставит потолок: менеджер не может выдать
больше, чем есть у него самого.

Практический смысл — вот эта комбинация, ради которой всё и строилось:

> оператор запускает профиль, но **не видит** пароль прокси и **не может**
> выгрузить cookies.

Технически это обеспечивается с двух сторон: сервер отдаёт хост прокси
замаскированным (`res***0236.provider.net`), а агент получает набор ограничений,
вычисленный на сервере, и запускает ядро с ними. Клиент их не выбирает.

## Резервные копии

```bash
sudo -u postgres pg_dump -Fc fury > fury-$(date +%F).dump
tar czf fury-bundles-$(date +%F).tar.gz -C /var/lib/fury bundles
```

Обе, и обе обязательны. База без бандлов — список профилей, которые нельзя
открыть; бандлы без базы — шифротекст, к которому нет ни ключей, ни версий.
Это не гипотеза: `download_bundle` отдельно ловит случай «строка есть, файла
нет» и объясняет его двумя причинами — восстановили базу без диска или подняли
сервер с другим `FURY_BUNDLE_DIR`
([server/src/api.rs:2827-2839](../server/src/api.rs)). Каталог задаётся
`FURY_BUNDLE_DIR` ([deploy/server-install.sh:143](../deploy/server-install.sh)).

Локальные данные каждый бэкапит у себя. Агент держит всё в одном каталоге —
`~/Library/Application Support/Fury` на macOS, `%APPDATA%\Fury` на Windows,
`$XDG_DATA_HOME/fury` на Linux, либо `FURY_HOME`, если он задан
([agent/src/paths.rs:17-39](../agent/src/paths.rs)). Команды `fury-agent status`
не существует: у агента есть `serve`, `relay`, `launch` и `check-fingerprint`
([agent/src/main.rs:55-79](../agent/src/main.rs)).

## Обновление

```bash
git pull && cargo build --release -p fury-server
```

Перезапустите. Миграции применятся сами. Схема меняется только вперёд:
удаляющих миграций нет, поэтому откат бинарника на предыдущую версию безопасен.

## Что появилось, и чего всё ещё нет

Три пункта, стоявшие здесь раньше, закрыты. Названы поимённо, потому что от них
зависят объём диска и рецепт бэкапа выше.

- **Синхронизация бандлов написана.** `POST` и `GET`
  `/v1/profiles/{id}/bundle` ([server/src/api.rs:2684-2850](../server/src/api.rs)):
  загрузку авторизует не только право, но и удерживаемый лок, а расхождение
  `x-fury-base-version` — это 409, а не молчаливая перезапись чужой сессии.
  Агент тянет бандл перед стартом и толкает после
  ([agent/src/sync.rs](../agent/src/sync.rs)).
- **Шифрование на клиенте написано.** Бандл пакуется и шифруется на машине
  оператора: XChaCha20-Poly1305, свой ключ данных на каждый бандл,
  запечатанный отдельно ([agent/src/bundle.rs:180-208](../agent/src/bundle.rs)).
  На сервер уходят шифротекст и завёрнутый ключ; расшифровать он не может и не
  должен.
- **Снятие чужого лока написано.** `POST /v1/profiles/{id}/lock` с `force`:
  разрешено только при `manage_access`, всегда пишется в аудит, и вытесненный
  агент своим heartbeat лок обратно не оживит
  ([server/src/api.rs:2445, 2465-2486, 2508, 2863-2877](../server/src/api.rs)).

Чего по-прежнему нет:

- **Браузер на чужой машине после снятия лока не закрывается.** Запись на
  сервере уходит, а агент того оператора видит лишь отказ heartbeat, пишет
  warning и продолжает — убивать работающий браузер из-за одного неудачного
  запроса нельзя ([agent/src/sync.rs:139-149](../agent/src/sync.rs)). Его
  следующая выгрузка будет отклонена, с текстом о том, что работа осталась у
  него на машине. См. [06](06-profile-sync.md).
