# 01 — Архитектура

## Принципы

1. **Спуфинг только в ядре.** Ни одной подмены через JS-инжект. Если что-то нельзя пропатчить в C++ — это не входит в продукт. Причина в [02](02-fingerprint-surface.md).
2. **Консистентность важнее уникальности.** Профиль генерируется из одного seed'а детерминированно, все значения выводятся из одной «персоны устройства». Валидный, но небывалый в природе набор — хуже дефолтного.
3. **Сервер не должен уметь читать данные.** Cookies, пароли и TOTP-секреты шифруются на клиенте. Сервер хранит шифротекст и метаданные.
4. **Локальный агент — единственный, кто трогает сеть профиля.** Браузер не ходит в интернет напрямую никогда: только через локальный релей.

## Компоненты

```
┌─────────────────────────────────────────────────────────────────┐
│ Рабочая машина (Windows / macOS)                                │
│                                                                 │

│  │  desktop (Tauri) │◄──────►│  agent (Rust, демон)           │ │
│  │  UI: проекты,    │  IPC   │                                │ │

│  └──────────────────┘        │  ├ relay   (127.0.0.1:PORT)    │ │
│           │                  │  ├ vault   (крипто, ключи)     │ │
```

### `core` — патченный Chromium

Не отдельное приложение с UI. Это браузерный бинарник, который агент запускает как подпроцесс,
передавая конфиг отпечатка. Ключевое решение: **конфиг читается один раз при старте процесса
и становится иммутабельным**. Никакого рантайм-обновления — иначе появляется канал, через
который страница теоретически может нащупать механизм подмены.

Способ передачи конфига — **не через командную строку**. Аргументы процесса видны другим
процессам в системе (`ps`, Process Explorer), а некоторые сайты через нативные приложения
это читают. Не pipe, а безымянный файл: создаётся 0600, тут же удаляется по имени и живёт
только как дескриптор. Pipe заставил бы агент до конца жизни браузера сидеть и дописывать
в него, потому что ядро читает конфиг до EOF (`agent/src/launcher.rs:259-303`). Дескриптор
всегда 3, в argv уходит только флаг `--fury-fp-fd=3` (`agent/src/launcher.rs:96`); флага
`--fury-fp-config` не существует, схема выше — упрощение.

Тем же способом и по той же причине с патча 0110 едет ключ, которым ядро шифрует cookies:
дескриптор 4, флаг `--fury-oscrypt-fd=4`, и только если ключ есть
(`agent/src/launcher.rs:185-187, 244-251`). В конфиге отпечатка ему не место — этот конфиг
ядро перепубликовывает в разделяемую память КАЖДОМУ дочернему процессу, включая рендерер,
а рендерер — тот самый процесс, который исполняет код посещаемого сайта.

### `agent` — локальный демон

Единственный компонент, который знает расшифрованные секреты. Живёт постоянно, потому что:
- держит heartbeat лока профиля на сервере (см. [06](06-profile-sync.md));
- обслуживает Local API для Puppeteer/Playwright/Selenium, который должен работать
  и когда UI закрыт;
- держит прокси-релеи для всех запущенных профилей.

Подмодули:

| Модуль | Ответственность |
|---|---|
| `launcher` | Разворачивание бандла профиля на диск, запуск/остановка процесса ядра, надзор |
| `relay` | Per-profile локальный прокси: авторизация в upstream, DNS, блокировка утечек |
| `vault` | Один машинный ключ в OS keychain (`dev.fury.agent` / `vault-key`, `agent/src/vault.rs:38-59`). Им запечатаны секретные колонки локальной БД и завёрнут ключ данных локального бандла. Ключ командного профиля приходит от оболочки готовым и через vault не проходит (`agent/src/bundle.rs:63-83`) |
| `sync` | Скачать бандл целиком, залить бандл целиком, heartbeat лока каждые 30 с (`agent/src/sync.rs:45-150`). Дельт нет. Разрешения конфликтов нет: 409 сервера показывается текстом. Лок берёт оболочка, агент только продлевает |
| `local_api` | REST на `127.0.0.1:35000` + выдача CDP WebSocket endpoint |
| `fingerprint` | Генерация конфига из seed + оверрайдов, валидация консистентности |

### `server` — self-hosted backend

Rust + axum + Postgres. Отвечает за: организации, проекты, пользователей, RBAC,
метаданные профилей, распределённый лок, хранение зашифрованных бандлов, аудит-лог.

Объектного хранилища нет и клиента к нему тоже. Байты бандла ложатся в каталог на диске
сервера: `bundle_root()` — это `FURY_BUNDLE_DIR` или `/var/lib/fury/bundles`
(`server/src/api.rs:2643-2647`), запись обычным `std::fs::write` (api.rs:2772), чтение —
`std::fs::read` по тому же пути (api.rs:2832). Колонка `bundles.s3_key` осталась от плана
и хранит относительный путь `<profile_id>/<version>.bundle`. В `server/Cargo.toml` нет ни
одного S3 SDK, в `docker-compose.yml` — только postgres и server. Для одной команды на
одной машине каталог и есть честный ответ; presigned URL в объектное хранилище — работа,
которая не сделана.

**Сервер намеренно тупой.** Он не генерирует отпечатки, не проверяет прокси, не расшифровывает
бандлы. Вся логика — на клиенте. Это позволяет self-host'ить его на самом дешёвом VPS
и не бояться его компрометации.

### `desktop` — Tauri 2 + React

Оболочка для агента. Tauri, а не Electron, по двум причинам: инсталлятор ~10 МБ вместо ~120 МБ
(а рядом уже лежит 200-МБ Chromium), и не хочется тащить второй Chromium в продукт,
который весь про Chromium.


## Три режима развёртывания

Решено после вопроса «зачем вводить сервер в первом окне?». Ответ: незачем.
Командный слой был построен первым и по недосмотру стал обязательным — это
перевёрнутый порядок, и он отсекает большинство пользователей.

| Режим | Что нужно поднимать | Кому |
|---|---|---|
| **Соло** | ничего | один человек, свои профили |
| **Команда, свой сервер** | один бинарник + PostgreSQL на VPS | агентство, команда |
| **Команда, чужой хостинг** | — | сознательно не делаем, см. ниже |

**Соло — режим по умолчанию.** Ни регистрации, ни аккаунта, ни сервера, ни БД.
Профили, прокси и персоны лежат локально; агент — единственный процесс, который
что-либо знает. Всё, что делает антидетект-браузер антидетект-браузером
(персона, шум, релей, изоляция), работает здесь целиком: командный слой не
добавляет к отпечатку ничего.

**Команда — включается настройкой**, а не встречает на первом экране. Появляется
сервер: организации, проекты, выдача доступа к проектам, распределённый лок,
аудит. Ставится на любой VPS: один бинарник и Postgres.

**Хостинг силами проекта — планируется, но с жёстким предусловием.** Первая
оценка была «не делать», потому что это означало бы держать у себя чужие cookies.
Оценка изменилась, когда стало ясно, что архитектура из [06](06-profile-sync.md)
уже отвечает на это: бандлы шифруются **на клиенте**, ключ на сервер не попадает,
сервер хранит шифротекст. Тогда «мы держим чужие данные» превращается в «мы
держим то, что сами прочитать не можем», и взлом отдаёт нечитаемое.

Отсюда порядок, который нельзя менять:

1. модуль `vault` и шифрование бандлов на клиенте;
2. синхронизация;
3. только потом хостинг.

Первые два пункта сделаны. `vault` написан (`agent/src/vault.rs`), бандл шифруется на
клиенте (`FURY-BN1`, XChaCha20-Poly1305, ключ данных на каждый бандл —
`agent/src/bundle.rs:138-210`), сервер видит шифротекст, завёрнутый ключ и дайджест
**шифротекста**. Синхронизация работает целиком, но без дельт: каждое закрытие профиля
льёт бандл полностью (`agent/src/ipc.rs:1426-1437`, `server/src/api.rs:2778` — `kind`
зашит строкой `'snapshot'`). Третий пункт, хостинг, не начат.

Self-host при этом остаётся полноправным вариантом, а не запасным: лицензия
AGPL-3.0-or-later закрепляет это с другой стороны — тот, кто поднимет на этом коде SaaS,
обязан открыть изменения.

## Стек и обоснование

| Что | Выбор | Почему |
|---|---|---|
| Ядро | Chromium fork | 65% рынка = самый обычный отпечаток. Firefox-ядро видно сразу |
| Агент | Rust | Один статический бинарник, нет рантайма, годится для сетевого релея |
| Сервер | Rust (axum, sqlx) | Тот же язык, что агент → общие типы в `shared`. Self-host = один бинарник |
| БД | PostgreSQL 16+ | Row-level security как второй рубеж под RBAC |
| Хранилище бандлов | Каталог на диске сервера | `FURY_BUNDLE_DIR`, по умолчанию `/var/lib/fury/bundles` (`server/src/api.rs:2643-2647`). S3 был планом: клиента в `server/Cargo.toml` нет, MinIO в `docker-compose.yml` нет, колонка `bundles.s3_key` хранит относительный путь |
| Desktop | Tauri 2 + React + TS | Малый вес, нативные webview |
| IPC desktop↔agent | Unix socket / named pipe | Не TCP — чтобы не светить порт |

Три языка (Rust, TypeScript, C++) — минимум для такого продукта. Добавлять четвёртый не надо.

## Модель процессов при запуске профиля

1. UI → agent: `launch(profile_id)`.
2. Agent → server: `POST /profiles/{id}/lock` (см. [06](06-profile-sync.md)). Отказ → выходим.
3. Agent: скачивает бандл, расшифровывает DEK через vault, разворачивает `user-data-dir` во временную папку.
4. Agent: поднимает `relay` на свободном порту, проверяет upstream-прокси, получает фактический IP.
5. Agent: если у профиля `auto_timezone`/`auto_geo` — резолвит из IP и вписывает в конфиг отпечатка.
6. Agent: `fingerprint::build(seed, overrides)` → JSON, валидация консистентности. Ошибка валидации → выходим с внятным сообщением, а не «как-нибудь запустимся».
7. Agent: spawn ядра, конфиг через pipe, `--proxy-server=127.0.0.1:<port>`.
8. Agent: ждёт CDP endpoint, публикует его в Local API.
9. Пока процесс жив — heartbeat лока каждые 30 с.
10. Выход: упаковка бандла → шифрование → загрузка дельты → снятие лока → затирание временной папки.

Шаг 10 — самое частое место багов в подобных продуктах. Если пользователь выключил ноутбук,
бандл не выгрузился, а лок отвиснет по TTL. Журнала незавершённых сессий на диске **нет**:
в `agent/src/` нет ни таблицы, ни файла с недогруженными бандлами, и при следующем старте
агент ничего не досылает. Работа остаётся в каталоге профиля и уедет при следующем
нормальном закрытии — если за это время никто не поднял версию на сервере, иначе выгрузка
упрётся в 409 (`agent/src/sync.rs:95-104`). Решением это станет, когда журнал появится.

## Что осознанно не делаем в v1

- Мобильные отпечатки (Android/iOS WebView). Это отдельное ядро, отдельная головная боль.
- Облачные («серверные») профили с запуском в браузере. Требует стриминга и парка машин.
- Свой прокси-сервис. Продаём/раздаём инструмент, а не трафик.
- Cookie-бот / прогрев. Легко добавить поверх Local API позже, ядром не является.
