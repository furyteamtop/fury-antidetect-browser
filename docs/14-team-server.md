# Сервер для команды: от пустой машины до выданных доступов

Это инструкция для того, кто держит сервер. Она описывает, что происходит на
каждом шаге и почему именно так — потому что половина шагов здесь про ключи, а
ключи прощают ошибки хуже всего.

Общая установка сервера — в [13-self-hosting.md](13-self-hosting.md). Здесь —
конкретный путь: развернуть, завести себя, завести команду, раздать доступы.

---

## 1. Что нужно от вас один раз

Свежая машина у провайдера отдаёт root с временным паролем, который она
требует сменить при первом входе. Сменить его должны вы: пароль, который знает
кто-то кроме вас, — это не пароль.

```bash
ssh root@ВАШ_АДРЕС
# провайдер сразу спросит текущий пароль, потом новый — придумайте свой
```

Пока вы там же, добавьте ключ той машины, с которой будете управлять сервером,
чтобы больше не вводить пароль:

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo 'ВАШ_ПУБЛИЧНЫЙ_КЛЮЧ' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Свой публичный ключ возьмите на своей машине: `cat ~/.ssh/id_ed25519.pub`.
Нет ключа — `ssh-keygen -t ed25519`.

После этого имеет смысл выключить вход по паролю совсем — тогда подбор пароля
перестаёт быть способом попасть на сервер:

```bash
sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl reload ssh
```

## 2. Развернуть

С вашей машины, из корня репозитория:

```bash
./deploy/push.sh root@ВАШ_АДРЕС ВАШ-АДРЕС-С-ДЕФИСАМИ.sslip.io
```

Второй аргумент — имя, на которое выпишется сертификат. Своего домена нет —
подойдёт `sslip.io`: адрес `203-0-113-7.sslip.io` резолвится в `203.0.113.7`,
и Let's Encrypt выдаёт на него настоящий сертификат. Приложение доверяет ему
без единой настройки. Появится домен — поменяете один аргумент и запустите
скрипт заново, он идемпотентный.

Скрипт ставит Postgres, собирает сервер из исходников, кладёт systemd-юнит с
урезанными правами, включает ufw (22, 80, 443) и Caddy, который сам получает и
продлевает сертификат. В конце он сам проверяет, что `/v1/me` отвечает ровно
`401 {"error":"unauthenticated"}` — приложение считает признаком «здесь Fury»
именно это, и установка не считается законченной, пока ответ другой.

Обновить сервер потом — та же команда.

### Если на машине уже есть другие сайты — Docker вместо push.sh

`push.sh` рассчитан на пустую машину: он ставит Caddy на порты 80 и 443, свой
Postgres и включает ufw. На сервере, где уже работают сайты через nginx и общий
Postgres, он сломает соседей. Так было у тестера 01.10.2026, и его команда
правильно не стала его запускать. Для такой машины — `docker compose` из корня
репозитория: Postgres и сервер в своих контейнерах, наружу только
`127.0.0.1:8901`, а TLS делает ваш nginx.

Раздел написан 02.10.2026 по файлам репозитория. На машине с Docker в этот день
его не прогоняли — Docker не было ни на одной из наших.

**Первый запуск.** Берите тег релиза, а не `main`: тег — это ровно то, что
собрано и выложено как версия.

```bash
git clone https://github.com/furyteamtop/fury-antidetect-browser fury && cd fury
git checkout v0.2.17                 # последняя версия со страницы релизов
cp .env.example .env                 # задайте FURY_DB_PASSWORD
docker compose up -d --build
curl -s http://127.0.0.1:8901/v1/me  # должно быть {"error":"unauthenticated"}
```

Данные живут в двух томах: `fury-db` (база) и `fury-bundles` (сами профили,
`/var/lib/fury/bundles` в контейнере). Пересборка и замена контейнера их не
трогает, `docker compose down -v` — стирает.

**nginx перед ним.** Обычный `server` с вашим сертификатом и `proxy_pass` на
`127.0.0.1:8901`, плюс три строки, без которых профили не пройдут:

```nginx
location / {
    proxy_pass http://127.0.0.1:8901;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # Профиль приходит одним запросом. Сервер принимает до 1 ГБ
    # (FURY_MAX_BUNDLE_BYTES), по умолчанию nginx режет на 1 МБ.
    client_max_body_size 1024m;
    # Отдавать тело серверу по мере получения, а не сначала целиком во
    # временный файл nginx.
    proxy_request_buffering off;
    # Агент ждёт передачу профиля до пяти минут; nginx по умолчанию — минуту.
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
}
```

Почему у тестера на старой машине выгрузка шла по 0,06–0,5 МБ/с, а на чистой
«всё летает», не выяснено: скачивание со старой было быстрым, и по логу клиента
сторону не определить. Если на общей машине выгрузка медленная, а `speedtest`
на клиенте показывает нормальный Upload — смотрите nginx и диск этой машины.

**Обновление** — четыре шага, и первый не пропускайте:

```bash
cd fury

# 1. Копии базы и профилей. Имя тома с профилями — с префиксом проекта,
#    обычно fury_fury-bundles; точное покажет `docker volume ls`.
docker compose exec -T db pg_dump -U fury fury | gzip > ~/fury-$(date +%F).sql.gz
docker run --rm -v fury_fury-bundles:/b -v "$HOME":/out debian:bookworm-slim \
  tar czf /out/fury-bundles-$(date +%F).tar.gz -C /b .

# 2. Нужная версия
git fetch --tags
git checkout v0.2.17

# 3. Пересобрать и заменить только сервер; база не перезапускается,
#    миграции применяются сами при старте
docker compose up -d --build server

# 4. Проверить
docker compose logs --tail=20 server      # последняя строка — "fury-server listening"
curl -s http://127.0.0.1:8901/v1/me       # {"error":"unauthenticated"}
```

**Откат** — только из копии. Миграции идут в одну сторону: старая версия
сервера на базе, которую уже обновила новая, не запустится и скажет, что не
знает применённую миграцию. Значит: вернуть тег, восстановить дамп из шага 1,
`docker compose up -d --build server`.

**Если сервер поднят по `docker-compose.yml` до 02.10.2026** — сначала найдите,
где лежат профили. В том файле не было тома для них, а образ не создавал
каталог, поэтому сервер в нём просто не стартовал (`cannot create the bundle
directory /var/lib/fury/bundles (Permission denied)`). Если у вас работает,
значит, вы задали `FURY_BUNDLE_DIR` или монтирование сами — проверьте, что это
том, а не каталог внутри контейнера:

```bash
docker compose exec server sh -c 'echo "${FURY_BUNDLE_DIR:-/var/lib/fury/bundles}"'
docker inspect "$(docker compose ps -q server)" --format '{{json .Mounts}}'
```

Если путь из первой команды не попадает ни в одно монтирование из второй,
профили живут в контейнере и пропадут при его замене. Вынесите их до
обновления и верните после:

```bash
docker compose cp server:/var/lib/fury/bundles ./bundles-before-update
# ... шаги 2-3 выше ...
docker compose cp ./bundles-before-update/. server:/var/lib/fury/bundles/
docker compose exec -u root server chown -R fury:fury /var/lib/fury/bundles
```

Если `FURY_BUNDLE_DIR` у вас задан другим путём, подставьте его вместо
`/var/lib/fury/bundles`.

**Если домен в Cloudflare — запись должна быть «DNS only» (серое облако), не
«Proxied».** Через прокси Cloudflare проходят маленькие запросы — вход, список
профилей, блокировки, — и поэтому всё выглядит рабочим. Но профиль команды
перед запуском скачивается с сервера целиком, а после закрытия браузера
выгружается обратно, и это десятки и сотни мегабайт. У прокси Cloudflare на
бесплатном тарифе потолок загрузки 100 МБ на запрос и 100 секунд ожидания
ответа сервера. Как это выглядит, снято 27.09.2026 у тестера с таким сервером:
запуск висит и падает с «the agent did not answer», в логе агента нет ни
«pulled bundle», ни ошибки, а после закрытия браузера — `could not tidy up …
error sending request for url (…/bundle)`. Caddy на сервере сам получает
сертификат, так что ничего, кроме переключения облака, делать не нужно.

## 3. Завести себя — владельца

На сервере никого нет, и пригласить вас некому, поэтому первое приглашение
выпускается из шелла:

```bash
ssh root@ВАШ_АДРЕС
source /etc/fury/fury.env && export DATABASE_URL
fury-server invite --email you@example.com --org "Моя команда"
```

Если сервер поднят не скриптом, а через `docker compose` из [13](13-self-hosting.md),
переменная уже внутри контейнера, и команда одна:

```bash
docker compose exec server fury-server invite --email you@example.com --org "Моя команда"
```

Получите код вида `5rrk-qgfr-gtyd-mw0f-sp12-axzy-0jsz-sx19`. Он живёт 48 часов,
срабатывает один раз, и сервер хранит только его хеш — потеряли, выпустите
новый.

В приложении: **«У меня есть приглашение»** → адрес сервера → код → пароль.

Дальше всё происходит на вашей машине: генерируется пара ключей X25519,
приватный ключ заворачивается в ключ, выведенный из пароля через Argon2id, и
рождается **ключ организации** — запечатанный на ваш публичный ключ. На сервер
уходит только завёрнутое.

> **Пароль восстановить нельзя.** Не «сложно» — нельзя. Ключ организации
> разворачивается только из него, и копии нет ни у кого, включая вас на
> сервере. Это цена того, что владелец машины не может прочитать прокси и куки
> своей команды. В менеджер паролей, сразу.

## 4. Завести остальных

Из приложения (владелец или админ): **Пользователи → Пригласить**, почта и роль.
Раздел в сайдбаре называется «Пользователи», не «Команда»
([desktop/src/i18n.ts](../desktop/src/i18n.ts), ключ `nav.users`).
Появится код — передайте его человеку. То же самое из шелла:

```bash
fury-server invite --email colleague@example.com --org-id <UUID> --role member
```

Человек вводит код у себя и заводит **свой** пароль. Вы его не знаете и знать
не должны.

### И дальше — шаг, который легко пропустить

После регистрации у человека есть аккаунт и **нет ключа организации**. Он
войдёт, увидит структуру команды и не расшифрует ни одного профиля. Это не
сбой: ключ запечатывается на его публичный ключ, а тот появляется только после
регистрации. Кто-то должен его впустить.

В приложении, у владельца или админа, в списке команды такой человек помечен
как ожидающий. **«Выдать ключ»** — и ваша машина распечатывает вашу копию
ключа организации и запечатывает её на его публичный ключ. Сервер получает
только результат.

Роли:

| роль | что может |
|---|---|
| `owner` | всё; один на организацию |
| `admin` | приглашать участников, выдавать ключ, создавать проекты, раздавать доступы; видит все проекты |
| `manager` | работать в выданных проектах и раздавать доступы внутри них |
| `member` | работать только в том, что ему выдали |

Админ не может выпустить второго админа: иначе доступ, полученный через один
администраторский аккаунт, переставал бы отзываться удалением этого аккаунта.

## 5. Раздать доступы к проектам

Проект — это единица доступа. Профили внутри наследуют его.

Владелец или админ создаёт проект и добавляет в него участника. Из приложения
это делается в двух местах, и наборы прав у них разные:

- **Пользователи → галочка проекта у участника** выдаёт фиксированную тройку —
  `view`, `launch`, `edit_profile` (`MEMBER_PERMS` в
  [Users.tsx](../desktop/src/components/Users.tsx), список записан в коде
  литералом). Смысл: «впустить в проект» значит видеть, открывать и править, и
  ничего опаснее;
- **Поделиться** на выделенных профилях
  ([ShareDialog.tsx](../desktop/src/components/ShareDialog.tsx)) — те же три
  плюс `reveal_secrets` отдельной галочкой: показать ли человеку пароль прокси.
  Локальный профиль при этом сначала уезжает на сервер.

Остальные шесть флагов — менять отпечаток, менять прокси, выгружать cookies,
создавать профили, удалять профили, раздавать доступ — сервер принимает
(`POST /v1/projects/{project_id}/grants`,
[server/src/api.rs](../server/src/api.rs); полный список —
[shared-rs/src/rbac.rs](../shared-rs/src/rbac.rs)), но экрана, где их
отмечают по одному, ещё нет. Сегодня они выдаются запросом к API.

Выданное **ограничено сверху ролью получателя**: менеджер не может выдать
участнику больше, чем участнику вообще положено. Проверяется на сервере, при
каждом запросе, а не при выдаче — отозвали доступ, и следующий же запрос уже
без него.

Отзыв снимает и блокировку профиля, если она у человека была: иначе его браузер
продолжал бы держать профиль занятым, а команда не смогла бы его открыть.

Чего отзыв **не** делает — не стирает то, что человек уже скачал себе на
машину. Честная граница любой системы, где работа идёт на компьютере оператора.
Поэтому смена сотрудника — это ещё и ротация ключа организации, и она есть:
удаление участника делает её сама, а кнопка «Заменить ключ организации» на
странице Пользователи — по требованию, например если потерян ноутбук, на котором
ключ лежал. Новый ключ запечатывается на всех, кто остался, и перешифровывает
каждый прокси; старая копия ключа перестаёт открывать что-либо новое
(`POST /v1/org/rotation`, [server/src/api.rs](../server/src/api.rs)).

## 5а. Безопасность аккаунтов команды — с 12.09.2026

Всё это на странице **Пользователи**, владельцам и админам; личная часть — в
**Настройки → Командный сервер**.

**Политика входа** (меняет владелец):

- *Второй фактор* — не требуется / на новом устройстве / при каждом входе.
  TOTP: любой аутентификатор. Участник без второго фактора при включённой
  политике **всё равно входит** и видит просьбу подключить его — запирать
  людей в день смены политики значит получить политику, которую выключат
  через час. Кто ещё не подключил, показано под настройкой.
- *Входить только с адресов* — список адресов и диапазонов. Вход с другого
  адреса отказывается **до** проверки пароля и записывается в журнал как
  «адрес отказан». Владельцы по умолчанию не ограничены — владелец, запершийся
  на своём же сервере опечаткой, звонить не может никому. Сервер отказывает
  сохранить список, в котором нет адреса, с которого его сохраняют.

**Журнал входов** — каждая попытка: кто, исход (вошёл, неверный пароль, адрес
отказан, запрошен код, неверный код), адрес, машина. Отдельно от аудита,
потому что у неудачного пароля ещё нет того, кто мог бы быть автором записи.
Три неверных пароля за четверть часа — событие `login.failed_burst` в аудите;
вход с незнакомой машины — `login.new_device`. Почту сервер не отправляет:
экран аудита — и есть оповещение.

**Кто сейчас в системе** — все живые сессии организации: машина, адрес,
последняя активность. «Завершить» — та машина выходит при следующем запросе,
для приложения это секунды. Свои сессии на других машинах — в настройках.

Адрес клиента сервер берёт из `X-Forwarded-For`, который ставит Caddy из
[server-install.sh](../deploy/server-install.sh). Сервер без обратного прокси
адреса не видит, и список адресов тогда отказывает всем — это правильный
отказ для настройки безопасности, которую нельзя проверить.

**Код ещё раз перед необратимым.** Галочка в политике «спрашивать код ещё раз
перед необратимыми действиями»: удаление профиля навсегда, удаление участника
(ротация ключа сама по себе не охраняется — она стоит всем лишь повторной
загрузки ключа), смена этой политики, завершение сессий участника. Код
действует десять минут на той сессии, где его ввели: вторая машина того же
человека спросит свой. Участник без второго фактора получает отказ на эти
действия, пока не подключит его; владелец без своего TOTP не может включить
галочку — иначе он не смог бы её выключить. Приложение само спрашивает код
при первом отказе (`desktop/src/stepUp.ts`), так что для организаций без
галочки диалог не появляется никогда.

## 6. Что дальше не работает

Здесь до 21.09.2026 стояли три пункта от 31.07: «профили на сервере не
создаются», «командного запуска нет», «UI команды не собран». Все три закрыты с
18.08.2026 — командный режим проходится целиком: профиль уезжает на сервер,
коллега открывает его на своей машине, лок держится, бандл возвращается
(README, «Командный режим работает целиком»). Абзацы стояли потому, что документ
не перечитывали, а не потому, что это было правдой.

Что не работает на самом деле, чтобы не искать:

- **Браузер на чужой машине после снятия лока не закрывается.** Запись на
  сервере уходит, а агент того оператора видит лишь отказ heartbeat и продолжает
  — убивать работающий браузер из-за одного неудачного запроса нельзя. Его
  следующая выгрузка будет отклонена. См. [13](13-self-hosting.md), конец.
- **Шесть из десяти флагов доступа выдаются только через API** — см. шаг 5.
- **Почту сервер не отправляет.** Ни кода приглашения, ни оповещений о входе:
  код передаёте сами, оповещение — экран аудита.

## Резервные копии

Две вещи, и обе обязательны:

```bash
sudo -u postgres pg_dump fury | gzip > /var/backups/fury-$(date +%F).sql.gz
tar czf /var/backups/fury-bundles-$(date +%F).tar.gz -C /var/lib/fury bundles
```

Сервер в Docker — те же две копии, командами из
