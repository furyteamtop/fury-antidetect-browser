# 06 — Синхронизация профилей

## Формат бандла

Бандл — слепок `user-data-dir` профиля Chromium, сведённый к необходимому минимуму.
Полная папка Chromium весит сотни мегабайт из-за кэшей; синхронизировать надо ~1-20 МБ.

**Так задумано, и так не сделано.** `pack()` кладёт в бандл ВЕСЬ каталог профиля, кроме
четырёх имён — `SingletonLock`, `SingletonSocket`, `SingletonCookie`, `lockfile`
(`agent/src/bundle.rs:161, 264-286`). Ни белого списка ниже, ни чёрного из следующего
абзаца в коде нет: `Cache/`, `Code Cache/`, `GPUCache/` и `Crashpad/` уезжают вместе с
cookies. Это и есть та «сотня мегабайт», о которой сказано в конце файла.

**Должны включать:**

```
Default/Cookies                    SQLite, основное
Default/Network/Cookies            новое расположение в свежих версиях
Default/Local Storage/leveldb/     localStorage
Default/Session Storage/           sessionStorage (по флагу профиля)
Default/IndexedDB/                 может быть тяжёлым, лимит по размеру
Default/Login Data                 сохранённые пароли Chromium
Default/Web Data                   автозаполнение форм
Default/Preferences                настройки профиля
Default/Bookmarks
Default/Extension State/
Default/Local Extension Settings/
Extensions/                        сами расширения (или только id + версия)
Default/Service Worker/            регистрации SW — часть сайтов без них ведёт себя иначе
```

**Должны исключать** (фильтра на это в коде нет, см. выше): `Cache/`, `Code Cache/`,
`GPUCache/`, `ShaderCache/`, `Crashpad/`, `GrShaderCache/`, все `*-journal`,
`Safe Browsing*`, логи.

**Ловушка с шифрованием Chromium.** `Cookies` и `Login Data` шифрует значения ключом
из OS keychain (DPAPI на Windows, Keychain на macOS). Скопированный на другую машину
бандл не расшифруется. Решения:

1. Патч в ядре, отключающий OS-привязку (`0110-os-crypt-key.patch`, написан). Ключ
   приходит НЕ из конфига отпечатка, а на отдельном дескрипторе (`--fury-oscrypt-fd=4`):
   конфиг перепубликовывается в разделяемую память каждому дочернему процессу, включая
   рендерер, который исполняет код посещаемого сайта. И не «от DEK профиля»: DEK у бандла
   случайный и меняется при каждой упаковке (`agent/src/bundle.rs:183`), а
   cookie-шифротекст обязан пережить пересохранение. Ключ выводится из ключа профиля,
   соседней ветвью от той, что заворачивает бандл: `subkey(profile_key,
   "fury-oscrypt-v1", profile_id)` (`shared-rs/src/keys.rs:238-263`,
   `agent/src/ipc.rs:1237-1238`). Бандл после этого переносим между машинами и ОС без
   конверсий.
2. Расшифровывать/перешифровывать в агенте при упаковке. Работает, но требует
   дублировать логику `os_crypt` для трёх платформ и ломается при её изменении upstream.

Взят вариант 1, патч написан. Что он закрывает и что нет:

- Ключ выдаётся только профилю, у которого он есть, то есть командному. Локальный
  профиль по-прежнему живёт на ключе машинного keychain — для того, что никуда не
  уезжает, это правильно (`agent/src/ipc.rs:1224-1238`).
- `IsCompatibleWithOsCryptSync()` возвращает true. Иначе расширенческие cookies, password
  reuse manager, GCM и device OAuth2 остались бы на машинном ключе: они спрашивают
  шифратор с `kEncryptSyncCompat`, а этот слот заполняют только провайдеры, отвечающие
  true.
- AES-256-GCM, а не AES-128-CBC платформенных провайдеров: GCM аутентифицирован, и
  неверный ключ падает честно, тогда как CBC распаддит мусор и оставит cookie-store
  заметить это по SHA-256(domain) — после чего он всё равно удалит всю группу eTLD+1.
- Чего патч НЕ чинит: просто неверный ключ по-прежнему уничтожает jar, потому что
  `net::CookieCryptoDelegate::DecryptString` не умеет сказать «недоступно» вместо
  «повреждено». Это ловится в агенте: рядом с профилем лежит отпечаток ключа
  (`Fury Key Id`), и при расхождении запуск отменяется до того, как браузер увидит
  каталог (`agent/src/ipc.rs:1239-1253`, `shared-rs/src/keys.rs:265-281`).

## Формат на диске и в S3

```
FURY-BN1            8 байт магии
nonce               24 байта
ciphertext          XChaCha20-Poly1305 над gzip(tar(каталог профиля))
```

`agent/src/bundle.rs:138-210`. Ни `manifest.json`, ни zstd, ни AES-256-GCM — этот абзац
описывал план, а не файл, и противоречил разделу «Формат бандла — реализован» в конце.
Отдельного манифеста нет вовсе: имена файлов лежат внутри tar, то есть внутри шифрования,
чего и требовалось. Метаданные, которые нужны серверу, едут рядом с байтами — завёрнутый
ключ и sha256 **шифротекста**, заголовками `x-fury-wrapped-key` и `x-fury-sha256`
(`agent/src/sync.rs:86-90`).

## Дельта-синхронизация

Полный бандл на каждое закрытие профиля — это десятки мегабайт на сессию и мгновенно
раздутый S3. Схема:

- Каждые N версий (по умолчанию 20) пишем полный снапшот.
- Между ними — дельты. Формат: `zstd --patch-from` (быстрый бинарный дифф на всём tar-архиве).
- Восстановление: последний снапшот + цепочка дельт до нужной версии.
- Старые версии подрезаются по политике (по умолчанию: 30 дней или 50 версий).

Версионирование даёт бесплатно то, чего у большинства конкурентов нет: **откат профиля
на предыдущее состояние**, когда сайт сломал сессию.

## Лок профиля

Одновременный запуск одного профиля с двух машин = два разных IP на одном аккаунте
в одну секунду = мгновенный бан. Лок обязателен.

```
POST /v1/profiles/{id}/lock
  → 200 { lock_token, expires_at }
  → 409 { holder: { user, machine, since } }
```

- TTL 90 секунд, heartbeat каждые 30.
- Heartbeat шлёт агент, пока процесс ядра жив.
- Отпустили лок → пометка «есть несохранённые изменения» снимается только после
  успешной загрузки бандла.
- **Force-unlock** доступен при праве `manage_access`, с обязательным подтверждением
  и записью в аудит. Нужен, когда у сотрудника упал ноутбук.

Гонка при force-unlock реальна: старый держатель может «проснуться» и выгрузить
устаревший бандл. Защита — `lock_token` в запросе на загрузку: сервер отвергает
загрузку с невалидным токеном.

## Конфликты

При корректной работе лока конфликтов не бывает. Они возникают при force-unlock
и при офлайн-работе. Политика — **без автоматического мержа**:

- Сервер отвергает загрузку, если `base_version` не равна текущей.
- Выбора агент не показывает — этого нет ни в агенте, ни в оболочке. 409 приходит
  текстом: «…your work is still here, on this machine, and nothing was overwritten»
  (`agent/src/sync.rs:95-104`). Локальная версия остаётся в каталоге профиля, и разбирать
  её приходится руками. Диалог из трёх вариантов — то, что осталось сделать.
- Мержить cookies двух версий автоматически нельзя: это ведёт к невалидным сессиям
  и выглядит для сайта как аномалия.

## Офлайн-режим

Агент должен уметь работать без сервера — иначе падение сервера останавливает работу
всей команды.

Локальному режиму сервер не нужен вовсе, и там всё работает без сети. Для командного не
написано ничего из перечисленного ниже: командный профиль в локальной базе не лежит — он
приходит от оболочки одним куском на каждый запуск (`agent/src/ipc.rs:1046-1062`),
TTL-кэша метаданных в `agent/src/store.rs` нет, локального лока нет, а колонка
`require_online` (`server/migrations/0001_init.sql:20`) не читается ни сервером, ни
оболочкой, ни агентом. Без сети командный профиль просто не запускается: запуск начинается
с `POST /lock`. Единственное, что переживает потерю связи, — уже развёрнутый каталог
профиля на диске.

- Метаданные проектов и профилей кэшируются локально (SQLite), TTL 7 дней.
- Бандлы кэшируются на диск в зашифрованном виде.
- Офлайн: разрешён запуск профилей, которые уже в кэше, **лок берётся локально**
  и помечается как ненадёжный. При восстановлении связи — сверка и, при необходимости,
  разрешение конфликта.
- Права проверяются по кэшу. Отзыв доступа применяется при следующем онлайне.
  Это осознанный компромисс; для организаций, которым он неприемлем — флаг
  `require_online = true`, отключающий офлайн-запуск.

## Формат бандла — реализован

`FURY-BN1` + 24-байтовый nonce + XChaCha20-Poly1305. Ключ **на каждый бандл**, и только он
заворачивается — но не всегда ключом машины. Заворачивающих ключей два, и выбор явный, без
умолчания: `Sealer::Machine` — ключ vault, для профиля, который живёт только на этой
машине; `Sealer::Shared` — `subkey(ORK, "fury-profile-v1", profile_id)`, для командного.
Первая версия знала только машинный ключ и ломала ровно ту функцию, ради которой всё
делалось: коллега, скачавший бандл, получал «the bundle key does not belong to this
machine» — правду, и ровно то, зачем бандл загружали. Префикс `fury:ork1:` говорит, каким
ключом завёрнуто, поэтому это поиск, а не угадывание, и бандл, упакованный до появления
общего ключа, по-прежнему открывается там, где был упакован, и при следующем закрытии
перезаворачивается общим (`agent/src/bundle.rs:63-136, 313-359`).

Почему не шифровать машинным ключом напрямую: из-за передачи. Отдать профиль
коллеге при одном ключе на машину — значит перешифровать весь каталог под его
ключ, каждый раз и для каждого получателя. С отдельным ключом данных передача
перезаворачивает 32 байта, а отзыв означает «больше не выдаём завёрнутый ключ»,
а не «перешифровываем всё, чего человек когда-либо касался».

Дайджест считается **от шифротекста**. Значит целостность может проверить тот,
кто расшифровать не может, — сервер верифицирует то, что хранит, и ключ при этом
никуда не уходит.

Не попадают в бандл: `SingletonLock`, `SingletonSocket`, `SingletonCookie`,
`lockfile`. Они описывают браузер, запущенный на другой машине; восстановленные
в другом месте, они дают профиль, который Chromium не открывает, а жалоба всегда
звучит как «профиль повреждён», а не «остался чужой лок».

Замерено на живом агенте: каталог с `SQLite format 3` и строкой
`warm-account-cookie` даёт бандл, в котором ни того, ни другого нет (37%
печатаемых байт — уровень случайного шифротекста), распаковывается в два файла,
cookie на месте, singleton-лок не поехал. Чужой завёрнутый ключ отклоняется.

**Ещё нет:** дельт. Сейчас бандл целиком — для профиля в сотни мегабайт это
дорого при каждом сохранении.
