# 18. Android-персоны на десктопном ядре

Запрос пришёл от пользователя 09.10.2026: «а он умеет мимикрировать под мобайл,
разные устройства?». До этого мобильные отпечатки стояли в «осознанно не делаем»
([01](01-architecture.md)) с формулировкой «отдельное ядро». [08](08-competitors.md)
уже сомневался в этой оценке; здесь она проверена замером.

## Что делают другие

ShardBrowser, 50 Android-персон из 220 (архив `ShardX-Fingerprints.zip`, md5
`e2f22d25690c2590b3e087a79e141bf2`, тот же, что качает их лаунчер; лицензии на
данные нет, поэтому в репозиторий не копируется, используется как справочник по
полям):

- персона Android — **тот же JSON**, что десктопная, и **то же ядро**. Лаунчер
  добавляет один мобильный флаг (DRM), всё остальное ядро делает само по полям
  `client_hints.mobile`, `screen`, `navigator.max_touch_points`;
- поля сверх наших: `client_hints.model`, `connection` (type, rtt, downlink),
  `battery`, `motion.carry` (hand / table / walking), `storage_estimate`,
  `webauthn.uvpa`, `window.inner/outer`, шрифты Android (`Roboto`,
  `Noto Color Emoji`, производительские);
- **голосов синтеза речи и кодеков в персонах нет** — эти вектора они не
  закрывают;
- признанные ими пределы: нет Widevine L1, шрифты, которых нет на машине,
  рисуются подменой; в трекере 200% CPU на macOS и некликабельная reCAPTCHA.

Octo: в мобильных профилях нет расширений и смены разрешения. Multilogin
сворачивает мобильные профили на десктопе в пользу облачных телефонов.

## Замер: эмуляция DevTools в нашем ядре

09.10.2026, ядро 155.0.8059.39 (macOS, M5), чистый профиль без конфига Fury.
Через CDP: `Emulation.setDeviceMetricsOverride` (384×832, DPR 2.8125,
`mobile: true`), `setTouchEmulationEnabled` (5 точек),
`setEmitTouchEventsForMouse`, `setUserAgentOverride` с метаданными Android
(модель SM-A546B). Затем `probe.html`.

**Главный фрейм и фреймы того же сайта — правильно:**

| Значение | Получено |
|---|---|
| userAgent, Client Hints | Android, `mobile: true`, модель |
| navigator.platform | `Linux armv81` |
| screen, DPR | 384×832, 2.8125, `portrait-primary` |
| maxTouchPoints | 5 |
| `pointer: coarse`, `hover: none` | да |
| ширина полосы прокрутки | 0 |
| layout viewport без `<meta viewport>` | 980, visualViewport scale 0.39 — как у настоящего Chrome на Android |

То есть механизм мобильной вёрстки, касаний и DPR в Blink уже есть
(`third_party/blink/renderer/core/inspector/dev_tools_emulator.cc`), отдельное
ядро не нужно.

**Утечки — всё, до чего эмуляция страницы не дотягивается:**

| Контекст | Что видно |
|---|---|
| iframe с другого сайта (отдельный процесс) | **весь десктоп**: Mac UA, `MacIntel`, экран 1470×956, DPR 2, 0 точек касания |
| SharedWorker, ServiceWorker | Mac UA, `userAgentData.platform = macOS`, `mobile: false` |
| Dedicated Worker | UA Android, но `platform = MacIntel` |
| везде | colorDepth 30 (у Android 24), `pdfViewerEnabled: true` и PDF-плагины, `navigator.hid` и `navigator.serial` |
| без конфига Fury | GPU Apple M5, 43 шрифта Mac, 10 ядер / 16 ГБ, `connection.type` отсутствует |

Кросс-доменный iframe — то, чем антифрод встраивается на страницу, поэтому
эмуляция через CDP как продукт не годится (и CDP у нас по умолчанию выключен,
`cdp: false`, см. README). Вывод: те же настройки Blink должны включаться
**из конфига Fury в каждом процессе рендерера и в каждом воркере**, как уже
сделаны остальные патчи — тогда согласованность между контекстами получается
тем же способом, что для десктопных персон.

## Сделано

**Шаг 1 (модель), 09.10.2026.** Персона с `os.name = "Android"` и блоком
`mobile`, правила согласованности, снимок с телефона превращается в персону.
В каталоге Android-персон нет: ни одного телефона ещё не сняли.

**Шаг 2 (патч 0130), 09.10.2026**, `core/verify/verify-0130.py`, 22 из 22, и
каждая проверка прогоняется дважды, с десктопным конфигом и с телефонным, и
обязана дать разный ответ:

| | десктоп | телефон, главный фрейм и **кросс-доменный iframe** |
|---|---|---|
| `ontouchstart`, `pointer`, `hover` | нет, fine, hover | есть, coarse, none |
| `navigator.connection.type` (и в Worker) | `undefined` | `cellular` |
| `pdfViewerEnabled`, plugins, mimeTypes | true, 5, 2 | false, 0, 0 |
| `screen.orientation`, `window.orientation` | landscape, нет | portrait-primary 0, 0 |
| WebHID, Local Font Access, Compute Pressure, Document PiP | есть | нет |
| `new Notification()` | создаётся | TypeError |
| ширина вёрстки без `<meta viewport>` | 500 (окно) | 980 |

Чего на десктопе нет и в Android есть, а патч НЕ включает: ContactsManager,
WebNFC, DigitalGoods, ContentIndex, DisplayCutoutAPI. Их интерфейсы браузер
привязывает только в сборке под Android, а запрос непривязанного интерфейса
десктопный браузер наказывает убийством рендерера: вызов
`navigator.contacts.select()` закрыл бы вкладку. Нужны заглушки-привязки.

Найдено по дороге: **окно Chrome на Mac не уже 500 пикселей**, поэтому при
экране 384 страница с `width=device-width` видела ширину окна 500, больше
экрана.

**Шаг 3, экран телефона (патч 0131), 10.10.2026**,
`core/verify/verify-0131.py`, 10 из 10. Виджет главного фрейма сам включает
`ScreenMetricsEmulator` (механизм режима устройства DevTools) из конфига:
страница с `width=device-width` верстается в 384, `innerHeight` = экран минус
рамка браузера (640), `devicePixelRatio` 2.8125, `outerWidth`/`outerHeight`
равны экрану, клик мышью попадает в элемент. Страница рисуется в левом верхнем
углу окна (позже по центру, 0134). Композитор вкладки рисует в
плотности телефона, а не экрана машины, иначе плотность машины видна по
округлению тонких рамок и `devicePixelContentBoxSize`. Служебные страницы браузера (`chrome://`, DevTools) остаются
десктопными и по вёрстке (0130), и по экрану (0131). При первой проверке
нашлось и исправлено: у страницы без `<meta viewport>` `outerHeight` выходил
1825 (внутренняя высота в уменьшенных пикселях плюс рамка), а `chrome://`
верстались в 980 с уменьшением.

**Шаг 4, касания вместо мыши (патч 0132), 10.10.2026**,
`core/verify/verify-0132.py`, 9 из 9, каждая проверка и на десктопном конфиге.
На телефонной персоне включается `TouchEmulator` браузера (режим DevTools
«касания из мыши») на каждой вкладке, кроме служебных: клик доходит до
страницы как `pointerdown:touch`, `touchstart`, `touchend`, совместимые события
мыши и `click` с pointerType touch, как у Chrome на Android; перетаскивание
прокручивает страницу пальцем; движение мыши без нажатия страница не видит.
Колёсико тоже палец: событий `wheel` нет, прокрутка идёт через `touchmove`.
Клики через CDP (так кликает агент по MCP) идут тем же путём. При первой
проверке нашлось и исправлено: `Input.dispatchMouseEvent` зависал навсегда,
потому что DevTools ждал подтверждения мыши, а мышь стала касанием.

## План

1. **Модель.** `os.name = "Android"` в схеме и в `persona.rs`, поля `model`,
   `mobile`, `connection`, `battery`, `motion`; правила согласованности в
   `fingerprint.rs` (Android ⇒ `Linux armv81`/`armv8l`, touch ≥ 1, полоса 0,
   avail = экран, colorDepth 24, GPU Adreno/Mali/PowerVR, шрифты Android).
2. **Патч ядра «мобильный режим»** по флагу конфига: настройки страницы
   (`viewport_enabled`, `viewport_meta_enabled`, primary/available pointer и
   hover, `main_frame_resizes_are_orientation_changes`, text autosizing), touch
   events, ориентация экрана, `connection.type`. В каждом рендерере, включая
   OOPIF, и в воркерах.
3. **DPR и окно.** ~~Страница видит экран телефона, а не окно~~ (0131),
   ~~окно открывается под телефон, и после восстановления сессии тоже~~ (0133;
   на macOS 500×751 при телефоне 384×832: Chrome не бывает уже 500).
   ~~Телефон по центру окна~~ (0134: в окне 500 колонка 384, по 58 с боков).
   ~~Утечки реального DPR~~ (10.10.2026, `core/verify/verify-0131-dpr.py`,
   26 из 26; телефон 2.8125, десктоп 1x и 1.25x на Mac 2x). У телефона до
   исправления четыре места выдавали 2: рамка 0.3px округлялась до 0.5 вместо
   0.356, и в кросс-доменном iframe тоже, `devicePixelContentBoxSize` блока
   100px был 200 вместо 281, paint worklet читал `devicePixelRatio` 2. Теперь
   композитор телефона рисует в его плотности (0131), worklet берёт плотность
   из конфига (0020), `screen.isExtended` у телефона false.
   `devicePixelRatio`, медиазапросы `resolution` и выбор в `srcset` были
   верны и до этого.
   У **десктопных** персон с плотностью не как у машины (1x и 1.25x на Mac
   2x) утекало то же самое плюс `srcset` (1x персона грузила 2x картинку) и
   рамка в кросс-доменном iframe. Исправлено 10.10.2026 тем же способом:
   страница и её кросс-доменные фреймы рисуются в плотности персоны, а
   iframe получает её с момента создания (иначе первый замер в нём был от
   машины). Окно, `innerWidth`/`innerHeight`, экран и его рабочая область, клик
   остаются как у хоста; при 1x точь-в-точь, при 1.25x и 1.5x `visualViewport`
   дробный, как на настоящем экране 125%/150%, а `innerWidth` никогда не шире
   окна. Полоса прокрутки, каретка, стрелка и список `<select>` считаются в
   плотности персоны: до этого 15px полоса персоны 1x на Mac 2x мерилась в 30.
   Цена: персона 1x на Retina рисуется в 1x и растягивается, текст
   мягче, как на настоящем экране 1x; персона 2x на экране 1x рисует вчетверо
   больше пикселей.
4. **Ввод.** ~~Клик мыши ⇒ тап, перетаскивание ⇒ свайп, без hover, колёсико ⇒
   палец, то же для MCP~~ (0132), ~~разброс точки касания~~ (0132: у профиля

   становятся двумя пальцами, страница видит два касания и масштабируется
   ровно на величину жеста).
5. **Скрыть десктопное:** PDF viewer и плагины, HID, Serial, File System

## Чего не будет

- **iPhone/iPad.** Safari — это WebKit; Chromium, называющий себя Safari,
  опознаётся по набору API быстрее, чем честный десктоп.
- **Отрисовка шрифтов и эмодзи, голоса синтеза речи, фактический вывод GPU** —
  от машины, на которой запущен профиль. Ограничение того же рода, что
  Windows-персона на Mac (README), только здесь оно касается каждой
  Android-персоны.
- **Аппаратный Widevine L1**: видео с аппаратной защитой на «телефоне» не играет.
