# 04 — Модель данных и права доступа

## Иерархия

```
Organization           — единица изоляции, свой корневой ключ шифрования
└── Member             — пользователь в организации с базовой ролью
└── Project            — контейнер профилей, точка выдачи доступа
    └── Profile        — браузерный профиль
        ├── Fingerprint   (seed + persona_id + overrides)
        ├── ProxyBinding  (ссылка на Proxy)
        ├── Bundle        (зашифрованный слепок user-data-dir, версионируется)
        ├── Credential[]  (логин/пароль/TOTP — отдельно зашифрованы)
        └── Lock          (кто запустил, heartbeat)
└── Proxy              — прокси организации, может быть привязан к проекту
└── AuditEvent         — журнал
```

Проект — единица выдачи доступа. Права на отдельный профиль **читаются**, но не выдаются:
`profile_grants` учитывается при разрешении прав и только добавляет к правам проекта, всё
равно упираясь в потолок роли (`server/src/rbac_guard.rs:88-103`), — а маршрута, который
создал бы такую строку, в API нет: в `server/src/api.rs:34-87` есть только
`/v1/projects/{project_id}/grants`. Основной сценарий — «дать сотруднику проект целиком»,
и сегодня он единственный.

## Роли

Базовая роль в организации:

| Роль | Смысл |
|---|---|
| `owner` | Владелец. Управляет организацией, ключами, участниками. Не удаляется |
| `admin` | Полный доступ ко всем проектам, управление участниками и прокси |
| `manager` | Создаёт проекты и профили, приглашает участников в свои проекты |
| `member` | Видит только явно выданные проекты |

Роль в организации даёт **потолок**. Фактический доступ к проекту задаётся отдельной
записью `project_grant` с набором прав.

## Матрица прав на проект

| Право | Что даёт |
|---|---|
| `view` | Видеть проект и список профилей, их статус и теги |
| `launch` | Запускать профиль |
| `edit_profile` | Менять имя, теги, заметки, настройки старта |
| `edit_fingerprint` | Менять персону, seed, оверрайды отпечатка |
| `edit_proxy` | Привязывать/отвязывать прокси |
| `reveal_secrets` | **Видеть пароли, TOTP-секреты и креды прокси в открытом виде** |
| `export_cookies` | Выгружать cookies/бандл на диск |
| `create_profile` | Создавать профили в проекте |
| `delete_profile` | Удалять профили |
| `manage_access` | Выдавать доступ к проекту другим |

### Ключевой сценарий: «оператор без секретов»

Набор `view + launch` без `reveal_secrets` и без `export_cookies` — то, ради чего команды
покупают такие продукты. Сотрудник открывает профиль, работает в уже залогиненном аккаунте,
но не может ни узнать пароль, ни унести cookies.

**Это должно быть обеспечено технически, а не проверкой в UI.** Реализация:

1. Хранилища паролей профиля пока нет вовсе, и автозаполнения тоже. Таблицы
   `credentials` и `autofill_tokens` в схеме есть
   (`server/migrations/0001_init.sql:206-232`), маршрутов к ним нет
   (`server/src/api.rs:34-87`), строка `Input.insertText` не встречается в репозитории
   ни разу, а `LaunchRestrictions::autofill_only` вычисляется
   (`shared-rs/src/rbac.rs:179`) и не читается никем. Так что `reveal_secrets` сегодня
   управляет одним настоящим секретом — кредами прокси (`GET
   /v1/proxies/{id}/credentials`, `server/src/api.rs:1570-1614`, аудит `proxy.reveal`).
   И даже он не защищает от того, у кого есть `launch`: релей на его машине дозванивается
   до прокси открытым паролем, а оболочка получает шифротекст кредов в `LaunchSpec` при
   каждом запуске (`desktop/src-tauri/src/commands.rs:933-936`).
2. При отсутствии `export_cookies` агент должен передать ядру два ключа — не один. Что за
   ними стоит:
   - `--fury-lock-devtools` (патч 0302) — отказ в `DevToolsAgentHostImpl::AttachInternal`,
     через который проходит каждая сессия, поэтому один заслон закрывает
     `--remote-debugging-port`, `--remote-debugging-pipe` и `chrome.debugger` разом.
     Заслон стоит на всех ПЯТИ входах в `IsInspectionAllowed` и **впереди** любой
     преференции. Первая версия имела два входа, проходила тест и оставляла обход:
     `prefs::kDeveloperToolsAvailabilityAllowlist` читается прямо из `Preferences` внутри
     user-data-dir — из файла, который у ограниченного оператора точно есть, — и одной
     строки в нём хватало, чтобы DevTools вернулись. Обход теперь проверяется в
     `core/verify/verify-0302.py`;
   - `--fury-lock-data-export` (патч 0303) — три отказа: CSV-экспорт паролей
     (`PasswordManagerPorter::Export`), HTML-экспорт закладок
     (`bookmark_html_writer::WriteBookmarks`) и выдача одного пароля в открытом виде
     (`PasswordsPrivateDelegateImpl::RequestPlaintextPassword`). Третий — потому что
     читать креды по одному это та же утечка, только медленнее, и путь доступен из
     `chrome://settings` независимо от `chrome://password-manager`. Каждый отказ стоит на
     функции, которая делает работу, а не на кнопке, которая её начинает: настройки
     ходят туда по Mojo, и расширение с нужным разрешением дойдёт вообще без кнопки.
     **На живом браузере не проверено** — все три пути WebUI/extension, до которых
     `core/verify` сегодня не дотягивается по CDP. Сборка доказывает, что отказы в
     бинарнике есть; что они срабатывают, не доказано.

   Чего в ядре НЕТ, хотя раньше было написано здесь: белого списка папок для сохранения
   файлов. Это задача `DownloadPrefs`/download-target и отдельного номера
   (`core/patches/series`, запись 0303).

   Временной папки с рандомным именем тоже нет: каталог профиля постоянный —
   `~/Library/Application Support/Fury/profiles/<id>` (`agent/src/paths.rs:47-49`), а
   `LaunchRestrictions::wipe_on_exit` вычисляется (`shared-rs/src/rbac.rs:178`) и не
   читается никем.

   CDP: `deny_cdp` действительно снимает `--remote-debugging-port` в `build_args`
   (`agent/src/launcher.rs:196-203`) — но только если ограничения до агента доехали, а
   сегодня они не доезжают.
3. Креды прокси не покидают агента — они подставляются релеем, в браузер попадает только
   `127.0.0.1:port` без авторизации.

**Честная оговорка:** от пользователя с правами администратора на своей машине защиты нет.
Он может снять дамп памяти процесса. Модель угроз здесь — «недобросовестный сотрудник
без специальных навыков», а не «мотивированный реверс-инженер». Это надо честно писать
в документации продукта, а не продавать как абсолютную защиту.

## Схема БД (PostgreSQL)

Полная версия — `server/migrations/0001_init.sql`. Ключевые решения:

- **UUIDv7** для сущностей: организации, пользователи, проекты, прокси, профили, бандлы
  (`Uuid::now_v7()` в `server/src/api.rs`). Не для всего: `audit_events.id` — `BIGSERIAL`
  (`0001_init.sql:257`), у `profile_locks` ключ это сам `profile_id`, у грантов —
  составной, у `autofill_tokens` — хэш токена.
- **Row-Level Security** описана в миграции (`0001_init.sql:278-311`) и **сегодня вторым
  рубежом не является**. Политики опираются на `current_setting('app.user_id')`, а
  единственная функция, которая его выставляет, помечена `#[allow(dead_code)]` и не
  вызывается ниоткуда (`server/src/rbac_guard.rs:139-149`). Сверх того сервер ходит в
  базу пользователем `fury` (`docker-compose.yml`), который создаёт таблицы и потому
  является их владельцем, — а владелец обходит RLS, пока не сказано `FORCE ROW LEVEL
  SECURITY`. Забытая проверка в хендлере сегодня отдаст чужие строки; единственный рубеж
  — `rbac_guard`.
- `project_grants` — таблица прав, а не enum-роль на проекте. Права — битовая маска
  в `BIGINT` плюс развёрнутое представление в API.
- Бандлы профилей **не в БД**. В БД только метаданные: `s3_key`, `version`, `sha256`,
  `size`, `wrapped_dek`.
- `profile_locks` с TTL: `expires_at`, продлевается heartbeat'ом. Отдельный индекс для
  быстрого поиска протухших.

## Аудит

Пишем в `audit_events` всё, что имеет значение при разборе «кто слил аккаунт»:

| Событие | Поля сверх общих |
|---|---|
| `profile.launch` | profile_id, proxy_id, ip, машина |
| `profile.stop` | длительность сессии |
| `secret.reveal` | credential_id, **какое именно поле**. Не пишется: хранилища кредов нет, см. выше. Раскрытие прокси пишется отдельно как `proxy.reveal` |
| `cookies.export` | profile_id, размер. Не пишется: экспорт делает агент по локальному сокету (`profile.cookies.export`, `agent/src/ipc.rs:791-863`), а у агента нет ни сессии на сервере, ни канала в аудит |
| `access.grant` / `access.revoke` | target_user, права до/после |
| `proxy.reveal` | proxy_id |
| `profile.delete` | снапшот метаданных |

Общие поля, которые действительно пишутся: `org_id`, `actor_user_id`, `action`,
`target_id`, `detail`, `at` (`server/src/api.rs:2926-2935`). Колонки `ip`, `user_agent`,
`request_id` и `target_kind` в таблице есть и всегда `NULL` — «кто слил аккаунт»
разбирается сегодня без адреса и без машины.

Аудит **должен быть append-only**: `REVOKE UPDATE, DELETE` для роли приложения. Сегодня он
не append-only. В миграции `REVOKE` лежит комментарием с пометкой «запустить
суперпользователем после создания роли приложения» (`0001_init.sql:313-315`), ни один
скрипт в `deploy/` его не выполняет, роли `fury_app` не существует, а `docker-compose.yml`
подключает сервер владельцем таблиц `fury`. Через сам продукт журнал не правится —
хендлера на это нет, — но правится напрямую в базе кем угодно, у кого есть `DATABASE_URL`.
Владелец организации не должен иметь возможности подчистить журнал через продукт, и пока
это держится на отсутствии кнопки, а не на правах.

## Шифрование: где какой ключ

```
User password ──Argon2id(kdf_salt, 256 МиБ, 3 прохода)──► User Key (UK)  [не покидает клиента]
                                │ разворачивает
                                ▼
                        Private Key (X25519)   на сервере лежит завёрнутым в UK
                                │ открывает
                                ▼
Org Root Key (ORK)   ЗАПЕЧАТАН НА ПУБЛИЧНЫЙ КЛЮЧ участника, а не завёрнут в его UK —
        │            иначе админ не мог бы выдать ключ тому, чьего пароля он не знает
        ▼ HKDF: subkey(ORK, "fury-profile-v1", profile_id)
Profile Key ──┬── заворачивает случайный ключ данных бандла (бандл — XChaCha20-Poly1305)
              └── subkey(…, "fury-oscrypt-v1", profile_id) — ключ, которым ядро шифрует
                  cookies (патч 0110). Отдельная метка, а не один ключ на два дела
```

- Сервер хранит только `wrapped_dek`, никогда сам DEK и никогда ORK в открытом виде.
- Отзыв доступа участника = удаление строки в `org_members` вместе с его грантами,
  сессиями и локами + **ротация ORK** (иначе он мог сохранить копию). Ротация не фоновая
  и не серверная: владелец или админ забирает материал (`GET /v1/org/rotation`),
  перезаворачивает всё у себя и присылает обратно одной транзакцией, в которой
  обновляются обёртки ORK всех остающихся участников и ключи данных ВСЕХ прокси
  организации (`server/src/api.rs:2274-2400`).
- Ключи бандлов там не обновляются, и это дыра, а не упрощение: ключ бандла завёрнут
  подключом старого ORK, после ротации он не разворачивается ничем, и каждый уже
  загруженный командный бандл перестаёт открываться (`agent/src/bundle.rs:110-126,
  221-226`). Заодно меняется и ключ cookies — это ловит метка `Fury Key Id` и отказ
  запуска с внятным текстом (`agent/src/ipc.rs:1239-1253`). До того как ротацией начнут
  пользоваться, перезаворачивание `bundles.wrapped_dek` должно попасть в ту же
  транзакцию.
- Каждому участнику генерируется X25519 пара при регистрации, приватный ключ обёрнут UK.
- Восстановление доступа при потере пароля: **невозможно** без recovery-ключа. При создании
  организации выдаём одноразовый recovery-код (обёртка ORK на нём) и заставляем его сохранить.
  Альтернатива для тех, кому это неприемлемо — режим «сервер знает ORK», явно помеченный
  в UI как менее безопасный.

Подробности формата бандла — [06](06-profile-sync.md).
