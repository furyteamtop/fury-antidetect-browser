# 04 — Модель данных и права доступа

## Иерархия

```
Organization           — единица изоляции, свой корневой ключ шифрования
└── Member             — пользователь в организации с базовой ролью
└── Project            — контейнер профилей, точка выдачи доступа
    └── Profile        — браузерный профиль
        ├── Fingerprint   (seed + persona_id + overrides)
        ├── ProxyBinding  (ссылка на Proxy)
        ├── Bundle        (зашифрованный слепок user-data-dir, версионируется)
        ├── Credential[]  (логин/пароль/TOTP — отдельно зашифрованы)
        └── Lock          (кто запустил, heartbeat)
└── Proxy              — прокси организации, может быть привязан к проекту
└── AuditEvent         — журнал
```

Проект — единица выдачи доступа. Права на отдельный профиль тоже поддерживаем, но это
исключение: основной сценарий — «дать сотруднику проект целиком».

## Роли

Базовая роль в организации:

| Роль | Смысл |
|---|---|
| `owner` | Владелец. Управляет организацией, ключами, участниками. Не удаляется |
| `admin` | Полный доступ ко всем проектам, управление участниками и прокси |
| `manager` | Создаёт проекты и профили, приглашает участников в свои проекты |
| `member` | Видит только явно выданные проекты |

Роль в организации даёт **потолок**. Фактический доступ к проекту задаётся отдельной
записью `project_grant` с набором прав.

## Матрица прав на проект

| Право | Что даёт |
|---|---|
| `view` | Видеть проект и список профилей, их статус и теги |
| `launch` | Запускать профиль |
| `edit_profile` | Менять имя, теги, заметки, настройки старта |
| `edit_fingerprint` | Менять персону, seed, оверрайды отпечатка |
| `edit_proxy` | Привязывать/отвязывать прокси |
| `reveal_secrets` | **Видеть пароли, TOTP-секреты и креды прокси в открытом виде** |
| `export_cookies` | Выгружать cookies/бандл на диск |
| `create_profile` | Создавать профили в проекте |
| `delete_profile` | Удалять профили |
| `manage_access` | Выдавать доступ к проекту другим |

### Ключевой сценарий: «оператор без секретов»

Набор `view + launch` без `reveal_secrets` и без `export_cookies` — то, ради чего команды
покупают такие продукты. Сотрудник открывает профиль, работает в уже залогиненном аккаунте,
но не может ни узнать пароль, ни унести cookies.

**Это должно быть обеспечено технически, а не проверкой в UI.** Реализация:

1. Сервер **не отдаёт** зашифрованные `Credential` клиенту без права `reveal_secrets`.
   Автозаполнение делает агент: получает одноразовый токен, тянет секрет по нему,
   вводит через CDP `Input.insertText` в конкретное поле, немедленно затирает из памяти.
2. При отсутствии `export_cookies` агент:
   - монтирует `user-data-dir` во временную папку с рандомным именем и затирает её при выходе;
   - в ядре включается флаг, отключающий `chrome://settings/passwords`, экспорт закладок,
     DevTools (`--fury-lock-devtools`) и сохранение файлов вне белого списка папок;
   - Local API не выдаёт CDP endpoint для этого профиля.
3. Креды прокси не покидают агента — они подставляются релеем, в браузер попадает только
   `127.0.0.1:port` без авторизации.

**Честная оговорка:** от пользователя с правами администратора на своей машине защиты нет.
Он может снять дамп памяти процесса. Модель угроз здесь — «недобросовестный сотрудник
без специальных навыков», а не «мотивированный реверс-инженер». Это надо честно писать
в документации продукта, а не продавать как абсолютную защиту.

## Схема БД (PostgreSQL)

Полная версия — `server/migrations/0001_init.sql`. Ключевые решения:

- **UUIDv7** для всех первичных ключей: сортируемы по времени, не раскрывают порядковый номер.
- **Row-Level Security** включена на всех таблицах с `org_id` как второй рубеж под RBAC
  приложения. Если в хендлере забыли проверку — RLS всё равно не отдаст чужие строки.
- `project_grants` — таблица прав, а не enum-роль на проекте. Права — битовая маска
  в `BIGINT` плюс развёрнутое представление в API.
- Бандлы профилей **не в БД**. В БД только метаданные: `s3_key`, `version`, `sha256`,
  `size`, `wrapped_dek`.
- `profile_locks` с TTL: `expires_at`, продлевается heartbeat'ом. Отдельный индекс для
  быстрого поиска протухших.

## Аудит

Пишем в `audit_events` всё, что имеет значение при разборе «кто слил аккаунт»:

| Событие | Поля сверх общих |
|---|---|
| `profile.launch` | profile_id, proxy_id, ip, машина |
| `profile.stop` | длительность сессии |
| `secret.reveal` | credential_id, **какое именно поле** |
| `cookies.export` | profile_id, размер |
| `access.grant` / `access.revoke` | target_user, права до/после |
| `proxy.reveal` | proxy_id |
| `profile.delete` | снапшот метаданных |

Общие поля: `org_id`, `actor_user_id`, `at`, `ip`, `user_agent`, `request_id`.

Аудит **append-only**: `REVOKE UPDATE, DELETE` для роли приложения. Владелец организации
не должен иметь возможности подчистить журнал через продукт.

## Шифрование: где какой ключ

```
User password ──Argon2id──► User Key (UK)  [не покидает клиента]
                                │
                                ▼ расшифровывает
Org Root Key (ORK) ────────────► обёрнут в UK каждого участника
        │                        (при добавлении участника ORK перешифровывается его публичным ключом)
        ▼ обёртывает
Profile DEK (случайный, на профиль)  ──► шифрует Bundle (AES-256-GCM)
Credential DEK                       ──► шифрует Credential
```

- Сервер хранит только `wrapped_dek`, никогда сам DEK и никогда ORK в открытом виде.
- Отзыв доступа участника = удаление его обёртки ORK + **ротация ORK** (иначе он мог
  сохранить копию). Ротация — фоновая перешифровка обёрток DEK, бандлы не трогаются.
- Каждому участнику генерируется X25519 пара при регистрации, приватный ключ обёрнут UK.
- Восстановление доступа при потере пароля: **невозможно** без recovery-ключа. При создании
  организации выдаём одноразовый recovery-код (обёртка ORK на нём) и заставляем его сохранить.
  Альтернатива для тех, кому это неприемлемо — режим «сервер знает ORK», явно помеченный
  в UI как менее безопасный.
