# 05 — Прокси и сеть

## Зачем нужен локальный релей

Chromium нельзя просто отдать прокси клиента. Причины, по каждой из которых уже нужен релей:

1. **Chromium не поддерживает авторизацию в SOCKS5.** Флаг `--proxy-server=socks5://user:pass@host`
   молча игнорирует креды. Работает только SOCKS5 без авторизации — а таких прокси на рынке
   почти нет.
2. **HTTP-прокси с авторизацией вызывает диалог** ввода логина/пароля, который надо
   перехватывать через CDP — то есть держать CDP-подключение к профилю, который должен
   быть чистым от следов автоматизации.
3. **Креды прокси не должны попадать в браузер.** Иначе сотрудник с доступом к профилю
   вытаскивает прокси организации.
4. **DNS.** Без релея Chromium может резолвить имена локальным резолвером → DNS-утечка,
   провайдер и сайт видят рассинхрон между гео DNS и гео IP.
5. **Точка контроля утечек** — единственное место, где можно гарантированно обрубить
   всё, что идёт мимо прокси.

Итог: браузер всегда запускается с `--proxy-server=http://127.0.0.1:<port>`, где `<port>` —
персональный порт этого профиля.

## Устройство релея

```
Chromium ──HTTP/CONNECT──► relay (127.0.0.1:P) ──► upstream (HTTP или SOCKS5)
                              │
                              ├─ авторизация в upstream (Basic для HTTP, RFC 1929 для SOCKS5)
                              ├─ DNS: только удалённый резолв (ATYP=domain / CONNECT по имени)
                              ├─ kill-switch: upstream не поднялся → 502 браузеру, не напрямую
                              ├─ стартовая страница профиля http://fury.invalid/, локально
                              └─ ошибки в tracing-лог

   UDP сюда не приходит вообще: релей — TCP-листенер. Фильтра исходящего UDP в нём нет и
   быть не может; WebRTC закрывает патч 0070, QUIC — ключ --disable-quic. Счётчиков
   трафика и RTT тоже нет — единственное измеренное число, которое видит оператор, это
   время ответа проверки прокси.
```

Поддерживаемые upstream:

| Тип | Примечание |
|---|---|
| HTTP | Только Basic (`Proxy-Authorization: Basic`, `relay.rs:340-342`). Digest не реализован |
| HTTPS | Схема принимается, но релей соединяется обычным TCP без TLS (`relay.rs:211-214`) — то есть работает как обычный HTTP-прокси. Настоящего HTTPS-прокси нет |
| SOCKS5 / SOCKS5h | username/password по RFC 1929. Всегда семантика `h`: адрес уходит апстриму как `ATYP=domain`, локального резолва нет ни в каком режиме и выключить это нельзя |
| SSH-туннель | **Не реализован.** `parse_upstream` (`main.rs:358-363`) знает четыре схемы — http, https, socks5, socks5h — и на любую другую отвечает `unsupported proxy scheme` |
| Ротационные по ссылке | Ссылка хранится с прокси и зашифрована (в ней обычно API-ключ), дёргается кнопкой: метод `proxies.rotate` (`ipc.rs:443-470`), запрос идёт *через* сам ротируемый прокси, потому что провайдеры привязывают ротацию к сессии. Политик «при старте» и «по таймеру» нет |

**Kill-switch обязателен и включён всегда.** Если upstream отвалился, релей не должен ходить
напрямую ни при каких условиях. Один запрос с реального IP убивает аккаунт, который вели
полгода. Поведение при обрыве, как оно сделано: не дозвонились до апстрима — пишем в лог и
отвечаем браузеру `502 Bad Gateway`, соединение закрываем (`agent/src/relay.rs:174-185`).
Сам релей при этом остаётся поднятым — специально, чтобы браузер продолжал получать
отказ, а не пошёл в обход (`agent/src/main.rs:131-132`). Прямого соединения не возникает
ни при каком исходе, потому что кода для него в релее просто нет. Чего нет и что этот
документ обещал: баннера в UI — ни строки про kill-switch в `desktop/src`. Оператор
видит отказ страницы, а не сообщение приложения. Это дыра в объяснении, а не в защите,
и она записана здесь, чтобы не выглядеть сделанной.

## Проверка прокси

Перед запуском профиля и по кнопке в UI:

```
GET через прокси → https://ipinfo.io/json
                   (или checker_url этого прокси, или FURY_IP_CHECK)
  ↓
ip, country, city, timezone, org, время ответа в мс
  ↓
запоминается НА ПРОКСИ: last_ip, last_country, last_timezone, last_location

Это всё. Классификации datacenter / residential / mobile / hosting / vpn / tor нет,
ASN нет, fraud score нет, проверки по чёрным спискам нет, замера скорости нет — ни в
агенте, ни в сервере. Колонки `last_asn` и `last_kind_detected` в схеме сервера есть,
и их никто не заполняет; список прокси показывает то, что в них лежит, то есть NULL.
```

Результат кэшируется на **прокси**, а не на профиль (`record_exit`, `agent/src/store.rs`),
потому что описывает выход, а не аккаунт. Флагов `auto_timezone` / `auto_geo` /
`auto_locale` больше нет: они лежали в схеме с самого начала, их никто никогда не читал
и не писал, и `server/migrations/0005_follow_the_exit.sql` их удаляет — столбец, который
никто не читает, это обещание, которое никто не держит. Правило теперь одно и выражено
самим значением: пустая таймзона у профиля значит «следовать выходу», заполненная —
«использовать её», и то же для языков. Таймзона, языки и координаты берутся из **одного**
ответа (`timezone`, `country`, `loc`), чтобы им нечем было разъехаться.

**Правило, и оно другое, чем планировалось здесь.** Запуск по несовпадению таймзоны и
гео IP никто не блокирует — такой проверки в коде нет. Вместо неё профиль по умолчанию
не имеет собственной таймзоны и берёт её у выхода прямо на запуске
(`agent/src/ipc.rs:1102-1151`), так что расходиться нечему: одно вычитание между
`Intl.DateTimeFormat().resolvedOptions().timeZone` и гео адреса, с которого пришёл
запрос, — это по-прежнему самый дешёвый детект в индустрии, и закрыт он тем, что второй
таймзоны просто не существует. Профиль с явно проставленной таймзоной запускается как
есть и ни с чем не сверяется: это выбор оператора, и он же способ выстрелить себе в
ногу. Если выход не ответил вовсе, профиль уходит на UTC и лог говорит об этом прямо —
«launching with UTC: this profile follows its exit and the exit did not answer», — а не
делает вид, что чему-то последовал.

Для self-hosted проекта важно, чтобы определение IP работало **без обязательных внешних
платных сервисов**. Как это выглядит сегодня: по умолчанию агент ходит на
`https://ipinfo.io/json` — бесплатно и без ключа, но это третья сторона, и она узнаёт о
существовании каждого проверяемого прокси. Это единственное место, где агент вообще
говорит с кем-то посторонним, и иначе нельзя: адрес выхода по определению может назвать
только дальний конец. Подменяется двумя способами — поле «checker URL» у конкретного
прокси и переменная `FURY_IP_CHECK` на всю машину; подойдёт любой URL, отдающий JSON с
`ip`, `country`, `city` и `timezone`.

Чего нет: офлайн-базы (MaxMind GeoLite2, DB-IP) и интеграции fraud score. Ни строки, и
до них дело не дошло.

## Защита от утечек — три рубежа

Утечка реального IP — главный способ потерять аккаунт. Дублируем защиту:

### Рубеж 1: ядро

- **WebRTC — патч 0070, и подмены кандидатов там нет.** Прежняя редакция этого документа
  обещала «host-кандидаты на правдоподобную приватную сеть, srflx — на IP прокси»; такого
  не делалось никогда, а до 02.08.2026 не делалось вообще ничего. Лаунчер с самого начала
  передавал `--force-webrtc-ip-handling-policy=disable_non_proxied_udp` — с комментарием,
  объясняющим, что именно это предотвращает. В M150 этот ключ читают
  `content/shell/browser/shell.cc:127` и browser-тесты; в `//chrome` его не читает никто,
  Chrome берёт значение из profile preference (`renderer_preferences_util.cc:157`) и
  только оттуда. Измерено 02.08.2026: наша сборка с прокси и с этим ключом отдавала
  странице `{host: 1, srflx: 1}`, и srflx нёс настоящий публичный адрес машины — один и
  тот же для всех профилей на ней, то есть связывал их между собой. Патч 0070
  переопределяет саму preference, и **три поля**, а не одно: `webrtc_ip_handling_policy`,
  плюс очистка `webrtc_ip_handling_urls` (per-URL запись отменяет политику) и
  `webrtc_local_ips_allowed_urls` (выключает mDNS-обфускацию, подставляя реальный
  приватный адрес). Обе на наших профилях пусты и всё равно чистятся: патч, чья
  правильность зависит от преференса, который никто пока не выставил, — не правильный.
  Неизвестную строку политики патч отвергает с ошибкой, а не превращает молча в
  `kDefault`: опечатка иначе не падала бы, а текла, потому что `kDefault` — это как раз
  режим, который собирает всё. Результат: браузер не собирает **никаких** кандидатов,
  `iceGatheringState` = `"complete"`. Это не выдуманное состояние — настоящий Chrome 150,
  непатченный, с той же enterprise-политикой в Preferences ведёт себя ровно так же.
  Проверка — `core/verify/verify-0070.py`, пять пунктов, включая контроль «ненастроенная
  сборка обязана течь»: контроль, который проходит и когда всё сломано, — не контроль.
- **QUIC выключен ключом `--disable-quic`, и это наше отличие от Chrome, а не паритет.**
  Патч не нужен: ключ садится ровно в то же поле, которое поставил бы патч, — поэтому
  0230 в серии закомментирован. Но записывать это как «мы как Chrome» нельзя: настоящий
  Chrome 150 договаривается об HTTP/3 с любым сервером, который его предлагает, а Fury не
  делает этого никогда, и это видно со стороны сервера, который анонсирует alt-svc и
  смотрит, придёт ли апгрейд. Владеет проблемой архитектура прокси, а не ядро: relay.rs
  говорит HTTP CONNECT и SOCKS5 CONNECT, оба TCP, а QUIC — UDP и пошёл бы мимо, ровно так
  же, как ходил WebRTC. Выход при этом архитектурно не заперт, вопреки прежней записи
  здесь: MASQUE-клиент (RFC 9298, UDP поверх HTTP/3) компилируется в бинарь безусловно, а
  проксирование QUIC заперто одним GN-дефолтом — `net/features.gni:70` ставит
  `enable_quic_proxy_support = is_debug`, а у нас `is_debug = false`. То есть дорога
  наружу — GN-аргумент плюс релей, умеющий MASQUE.
- **Отключены сервисы, ходящие в сеть мимо профильного прокси**, но список не тот, что
  был. Safe Browsing выключен патчем 0901: дефолт `kSafeBrowsingEnabled = false`. Одного
  `--disable-background-networking` не хватало — он останавливает скачивание базы
  (`v4_update_protocol_manager.cc:106-109`), а отчёт по каждой загрузке всё равно уходил
  на зашитый `sb-ssl.google.com`, который не закрыт никаким API-ключом; браузер при этом
  ничего не защищал и показывал в настройках «стандартную защиту». Обновления компонентов
  **не отключены, и это несущее решение**: `--disable-component-update` из лаунчера убран,
  потому что Chromium регистрирует вложенный в бандл Widevine CDM именно через путь
  регистрации component updater. Измерено 02.08.2026: один и тот же бинарь отвечает на
  `requestMediaKeySystemAccess("com.widevine.alpha")` `available` при запуске напрямую и
  `NotSupportedError` при запуске с этим ключом. Что ключ давал взамен: ничего — с ним и
  без него браузер за 90 секунд открывает соединения к одному и тому же набору
  google-адресов, и под Fury все они идут через релей, потому что `--proxy-server`
  указывает на него, а loopback-исключение снято (`--proxy-bypass-list=<-loopback>`).
  Вопрос никогда не стоял «говорит ли браузер», только «с чьего адреса». Что реально
  передаётся: `--disable-background-networking`, `--disable-domain-reliability`,
  `--disable-breakpad`, `--safebrowsing-disable-auto-update`
  (`agent/src/launcher.rs:88-181`). Отдельных ключей про DNS-prefetch и Network Time
  лаунчер не передаёт.

### Рубеж 2: релей

- Все TCP-соединения только через upstream, kill-switch.
- DNS только удалённый. Локальный резолв запрещён.
- UDP не проксируется вообще, и оговорки про SOCKS5 UDP ASSOCIATE больше нет: такого кода
  в релее не существует — `socks5_connect` отправляет только `CMD=0x01`, а слушает релей
  TCP. Серия (запись про 0230) отдельно фиксирует, что дорога к UDP через прокси — это
  MASQUE (RFC 9298) плюс GN-аргумент `enable_quic_proxy_support`, а не ASSOCIATE. За
  WebRTC отвечает патч 0070, за QUIC — `--disable-quic`; в релей этот трафик не попадает
  ни в каком виде.

### Рубеж 3: ОС (опционально, «параноидальный режим»)

**Не реализовано — это план, а не рубеж.** Ни `pfctl`, ни anchor, ни WFP не упоминаются
нигде в `agent/`, `desktop/` и `server/`.

Как задумано: правило файрвола, разрешающее процессу ядра исходящие соединения **только**
на `127.0.0.1:<port>`. На macOS — `pf` anchor, на Windows — правило WFP по пути к бинарю.
Требует прав администратора, поэтому опция, а не дефолт. Ценность в том, что это
единственный рубеж, который держит, даже если в ядре нашлась дыра, — и ровно поэтому его
отсутствие записано здесь, а не подразумевается сделанным.

## Привязка прокси

- Прокси — сущность организации, лежит в общем пуле.
- Может быть привязан к проекту (тогда виден только в нём) или общий для организации.
- Один прокси на один профиль — дефолт. Разрешить один прокси на несколько профилей
  можно, но UI обязан предупредить: несколько аккаунтов с одного IP — типовой признак
  фермы для антифрода. Показываем счётчик «профилей на этом IP».
- Креды прокси видны только при праве `reveal_secrets` ([04](04-data-model-rbac.md)).

## Local API для автоматизации

`127.0.0.1`, порт из `FURY_API_PORT` — эта же переменная его и **включает**. Без неё API
не поднимается вовсе, `0` и любой мусор тоже оставляют его выключенным, то есть опечатка
закрывает, а не открывает (`agent/src/main.rs:37-42`). Число, которое код называет своим,
— 35000, и оно намеренно не совпадает ни с одним конкурентским (AdsPower :50325,
Dolphin :3001, Octo :58888): скрипт, направленный не в тот продукт, должен не соединиться,
а не заработать наполовину.

Токен генерируется при первом запуске в файл `api-token` рядом с базой, режим 0600, и
предъявляется как `Authorization: Bearer`. Кроме токена — два отказа, и они и держат
страницы снаружи: запрос с заголовком `Origin` получает 403 **до** сверки токена (браузер
этот заголовок шлёт, скрипт нет), и `Host` обязан быть loopback — иначе имя, резолвящееся
в 127.0.0.1, делает этот порт same-origin для страницы, то есть DNS rebinding снимает
первый отказ.

```
GET  /v1/status
GET  /v1/profiles
GET  /v1/proxies
GET  /v1/personas
POST /v1/profiles/start   {"id": "…", "cdp": true}
                          → { pid, relay_port, debug_port?, ws_endpoint? }
POST /v1/profiles/stop    {"id": "…"}
```

Идентификатор едет в теле, а не в пути. Маршрутов `/{id}/status` и `/{id}/proxy/rotate`
нет: ротация доступна только приложению по сокету (`proxies.rotate`). Каждый маршрут —
ровно один IPC-метод, чтобы HTTP-поверхность не могла разъехаться с тем, чем пользуется
само приложение, и оказаться неправильной отдельно.

`ws_endpoint` подключается напрямую в Puppeteer/Playwright:

```js
const browser = await puppeteer.connect({ browserWSEndpoint: wsEndpoint });
```

Выдаётся только если у пользователя есть право `export_cookies` — потому что через CDP
можно вытащить всё. Без права `start` вернёт `403` с пояснением.
