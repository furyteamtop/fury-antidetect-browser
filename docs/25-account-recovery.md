# 25 — Восстановление доступа и передача владения

Решено 13.11.2026. Повод: тестер на своём сервере забыл пароль владельца. Сессия
живёт 12 часов, обновление перезапустило приложение, вход попросил пароль, и
пути назад не было: команда с её профилями и прокси осталась за паролем.

## Почему «сбросить пароль» нельзя

Цепочка ключей (`shared-rs/src/keys.rs`):

```
пароль ──Argon2id──► ключ пользователя ──► закрытый ключ X25519 ──► ключ организации ──► данные
```

Сервер хранит закрытый ключ только зашифрованным. Если на сервере просто
заменить хэш пароля, новый пароль не откроет старый закрытый ключ, и всё, что
зашифровано для команды, станет нечитаемым. Поэтому восстановление — это второй
замок на тот же закрытый ключ, а не сброс.

## Ключ восстановления

- **Что это.** 32 случайных байта, показанные как 52 символа Crockford base32
  группами по 4 (как коды приглашений). Создаётся на клиенте, показывается один
  раз. Сервер видит только производные, из которых ключ не восстановить.
- **Что хранит сервер** (`users`): `recovery_salt`; `recovery_wrapped_key` —
  закрытый ключ, зашифрованный ключом из кода (Argon2id → HKDF «wrap»);
  `recovery_auth_hash` — Argon2id-хэш отдельной производной кода (HKDF «auth»,
  без соли: соль лежит на сервере, и если бы клиенту она была нужна до проверки
  кода, сервер выдавал бы её по любому адресу и тем самым говорил, у кого есть
  ключ). По хэшу сервер узнаёт, что код верный, не получая ключа для расшифровки.
- **Кто создаёт.** Любой участник, в настройках, с повторным вводом пароля (и
  кодом 2FA, если она включена). Владельцу приложение показывает полосу
  «сохраните ключ восстановления», пока ключа нет, и предлагает его сразу при
  создании команды. Новый ключ заменяет старый.

## Как проходит восстановление

1. «Забыли пароль?» на экране входа: почта и ключ восстановления.
2. Клиент выводит из кода «auth» и отправляет. Сервер сверяет хэш. Пять неудач
   за час на адрес закрывают попытки на час. Неверный адрес и неверный код
   отвечают одинаково.
3. Второй шаг, по решению владельца продукта:
   - включена 2FA → код из приложения;
   - иначе на сервере настроена почта → шестизначный код на почту аккаунта;
   - иначе **ожидание 24 часа**. Все админы и владелец команды, а также все
     живые сессии этого аккаунта сразу видят полосу «восстанавливается доступ к
     аккаунту …» и могут отменить.
4. Сервер отдаёт `recovery_salt`, `recovery_wrapped_key`, публичный ключ и
   случайный вызов, запечатанный на публичный ключ.
5. Клиент открывает закрытый ключ кодом и проверяет, что он соответствует
   опубликованному публичному: сервер не может подсунуть чужой ключ. Открывает
   вызов (это доказательство владения закрытым ключом), задаёт новый пароль,
   заново шифрует закрытый ключ и **сразу создаёт новый ключ восстановления**:
   использованный больше не действует.
6. Сервер в одной транзакции меняет хэш пароля, соль, зашифрованный ключ и
   ключ восстановления, отзывает все сессии аккаунта, пишет в журнал
   `account.recovered` и выдаёт новую сессию.

Ключ организации не меняется: он запечатан на тот же публичный ключ, поэтому
профили, прокси и доступы остаются как были.

## Передача владения

В команде один владелец. Теперь он может, пока может войти, передать владение
админу, который уже впущен в команду (держит ключ организации): повторный ввод
пароля (и 2FA, если включена). В одной транзакции владелец становится админом,
админ — владельцем; запись `org.owner_transferred` в журнале. Других путей
сменить владельца нет; `set_member_role` по-прежнему отказывает в роли owner.

## Угрозы

| Кто | Что получает |
|---|---|
| Украденная база | Ничего: хэш «auth» и зашифрованный ключ без 256-битного кода бесполезны. |
| Враждебный админ сервера | Не может восстановить чужой аккаунт без кода. Ограничение прежнее: он видит пароль при входе (docs: `keys.rs`). |
| Укравший почту | Без кода ничего. С кодом и почтой — да; поэтому 2FA, если включена, имеет приоритет над почтой. |
| Укравший только код | При 2FA или почте — ничего. Без них — 24 часа, в течение которых админы и сессии владельца видят полосу и отменяют. |
| Коллега-админ | Не может стать владельцем без действия самого владельца. |
| Чужой за открытым ноутбуком | Не создаст новый ключ без повторного ввода пароля. |

## Чего это не решает

Аккаунт, у которого ключа восстановления не было, восстановить по-прежнему
нельзя. Для такого случая остаётся путь через админа: пригласить на другой адрес
и впустить, без прав владельца. Самостоятельно размещённому серверу для всего
этого нужно обновиться до версии с миграцией 0022.
